# 老项目升级 doc-framework —— 交给 AI 的上下文

> **怎么用**：在要升级的**老项目**里新开一个 AI 会话，把「===== 可粘贴上下文开始/结束 =====」之间整段粘贴，无需准备。AI 会先解析最新 tag → 只读勘察 → 差异报告，确认后才动手。
>
> 给**使用者**的升级操作包，不是框架开发文档。**迁移动作以第 4 步为唯一权威**；升级机制见 `docs/设计文档.md` §9.3。**不写死版本**：目标 = GitHub 最新 tag，执行时解析。

## 任务：把本项目的 doc-framework 升级到 GitHub 最新 tag

本项目用 doc-framework 初始化过（项目根有 `doc-framework/` 文档根与 `AGENTS.md` 引导段），现在对齐到**当前版本**。安装与升级只有一个 CLI 入口 **`doc-framework install`**，取包走 **GitHub tag**（没有 npm 发布、没有 `install.sh`、没有 `postinstall`）。

**版本口径**（开工第一件事，之后每一步的 `<目标版本>` 都指它）：

```bash
git ls-remote --tags --refs https://github.com/knight-peter/doc-framework.git 'v*' \
  | sed 's|.*refs/tags/||' | sort -V | tail -1      # 例：vX.Y.Z
```

- 钉依赖用同一 tag：`"doc-framework": "github:knight-peter/doc-framework#<目标版本>"`；
- 哨兵与 skill marker 的 `version` 都写 **`v` + `package.json` 的 version**（tag 去掉前导 `v` 应一致），从 `node_modules/doc-framework/package.json` 读；未装依赖时读临时 clone 的同 tag 目录。

### 第 2 步：升框架（机器动作，安全）

- **原有 git 依赖**：`package.json` 的 `doc-framework` 改成 `"github:knight-peter/doc-framework#<目标版本>"` → `npm install`（或 `pnpm install`）→ `npx doc-framework install`（pnpm 项目 `pnpm exec`）。**不需要 `onlyBuiltDependencies`**（已无 postinstall）。
- **原先用 `install.sh`**：装 Node ≥22 → 项目根跑 `npx --yes "github:knight-peter/doc-framework#<目标版本>" install`；不需要 `package.json`。

> 只升 skill、不动依赖：`npx --yes "github:knight-peter/doc-framework#<目标版本>" sync`（定制逐个跳过）；`install` 是强制刷新（覆盖定制 skill，但**不动文档与 AGENTS 永久段**）。

**边界**：这些命令**只动 skill 文件**，绝不重命名、移动或改写 `doc-framework/` 文档根与 `AGENTS.md`。升完 skill 只是第一步，**文档体系必须走第 4 步人工迁移**。

### 第 3 步：核验框架已升级

8. **应用规范四不写清理**：删变更痕迹（版本号/日期/`来源=`/修订沿革）、代码清单（回链路径）、缺口待办（→ 计划）；「禁止 X」的否定性结论要留。
9. **跨应用共享约定上移 `边界/`**：两个及以上应用规范出现的同主题约定 → `边界/{能力}边界.md`，应用规范只留本端机制。
10. **深度主题拆分册**：单节 >80 行或小节 >8 个的应用规范，深度主题拆到 `规范/{应用标识}-{主题}.md`，并在 §3.1 索引登记（`check` 机检索引 ↔ 分册一致）。
11. **删应用规范 §6「技术栈特有检查项」**：检查项并入各分册的检查项节。

#### 顺手对齐

12. **哨兵**：这次改到的全局文档 / 计划模板 / 契约，首行补 `<!-- doc-framework:docstruct v<框架版本> | 全局文档结构版本；… -->`——照抄模板原文，只把 `{{框架版本}}` 换成开工读到的 `package.json` version（前加 `v`），说明文字一字不改。**落后于框架版本会让 `check` 失败（⚠️）**；完全缺失只报 ℹ️，但按当前规范要补——改到哪份补哪份。R4 只校验四份全局文档 + 在途计划，模块契约哨兵不逐模块比版本。

### 第 5 步：验收（必须做）

1. `check` 全绿（命令同第 1 步）；ℹ️ 不影响退出码，但要逐条解释。
2. 哨兵版本 == `v<package.json 的 version>`；marker 的 `version` 同值，且没有意外的"本地已定制"跳过。
3. P0 三项逐模块确认到位：AGENTS 纪律段 / 契约 §9 / **总契约模块单表**。
4. 出**验收报告**：基线输出 vs 现在（差异逐行说明）、已迁移项、**未完成项 + 卡在哪**、需用户决定的遗留项（如归档计划是否清理——**归档不删文件是纪律，清理由是人的决定**）。

### 硬性禁止（越界即停下问）

1. **不自动迁移文档结构**：无逐批确认不许批量重写契约/总契约/计划；不许顺手"美化"没被要求的章节。
2. **不删任何文档**：归档只做"`合并状态=已合并` 且契约已承接 → `git mv` 进 `计划/归档/`"；是否清理由人决定。（例外：P0-2 的 §9 旧表删除。）
3. **不擅自改依赖与 CI**：除第 2 步那一个依赖 tag，其他依赖/脚本/CI 不动。
4. **不动上游 tag 与版本**：不在框架仓库新建/移动/删除 tag，不改官方 `package.json` 版本——发版是人的动作，你只读。
5. **不整份覆盖模板**：项目档案与契约是**自有资产**，只"对齐"不"回灌"。
6. **拿不准的项列成待决清单交用户**，尤其 P3 里需逐条裁决的内容项（哪些是跨应用共享约定、哪些该拆册）。
