## 任务：把本项目的 doc-framework 从旧版本升级到框架仓库的最新 tag

本项目在早期用 doc-framework 初始化过（项目根有 `doc-framework/` 文档根与 `AGENTS.md` 引导段），现在要升级到框架的**最新已发布版本**。框架仓库（官方权威来源）在你**可读**的路径：`<在这里填框架仓库绝对路径，例如 /Users/xuqi/Learn/doc-framework>`。

> **本次升级特别说明（v2.6.1）**：v2.6.1 **改了 skill 文件**——`/module-doc` 的模式代号 `M`/`B`/`C` 全部改成中文处理方式名（名字即语义），工具侧的契约章节映射与增量解析也一并加固。所以第 3 步的 `sync` 是**必做动作**（不是可选），否则新会话里 AI 仍会冒出字母代号。文档结构未变，第 4 步的迁移大概率只需确认 `AGENTS.md` 措辞已对齐——旧模板渲染出的字母后缀（`/module-doc` 后跟 `M` / `B`）建议改成 `/module-doc`（合并增量）/ `/module-doc`（代码对账）。

> **版本口径（先看这条，后面全用它）**：**升级目标 = 框架仓库的最新 tag，不是某个写死的版本号**。本提示词不写死版本；你**开工第一件事**就是把它解析成具体值，之后每一步提到的 `<目标版本>` 都用它：
>
> ```bash
> git -C <框架仓库路径> fetch --tags                        # 先确保本地知道远端的新标签
> git -C <框架仓库路径> describe --tags --abbrev=0         # 最新 tag ⇒ <目标版本>，形如 v2.4.0
> node -p "require('<框架仓库路径>/package.json').version"  # 该仓库当前声明的版本，形如 2.6.0
> ```
>
> 两个值得**都记下来并各用其位**：钉依赖用 **tag**（`#<目标版本>`）；文档结构**哨兵**写 **`package.json` 的 version**（前面加 `v`）——哨兵要与代码里的版本一致，否则 `check` 的 R4 会误判。两者不一致是**正常且已存在**的情况（本仓库目前 `package.json` 领先最新 tag），**遇到不要"纠正"任何一方，也不要自作主张新建 / 移动 tag**（发版是人的动作），按上面各用其位即可。
>
> 顺便把结果写进第 1 步的差异报告（表里已留「目标版本」一行）：**项目现状版本 → 目标版本**。

### 第 2 步：升框架（机器动作，安全）

按本项目原来的安装方式二选一：

- **npm/pnpm git 依赖**：把 `package.json` 里的 `git+https://github.com/knight-peter/doc-framework.git#<旧版本>` 改成 `#<目标版本>`（= 开工时解析出的最新 tag）→ `pnpm install`（lockfile 锁死时用 `pnpm update doc-framework`；若 store 复用跳过了 postinstall，用 `pnpm rebuild doc-framework`）。
- **一键脚本**：重跑安装脚本。

> 若本项目只想要最新 skill 而不改依赖：`npx doc-framework sync`（等价物）。

**这一步的边界（框架纪律，务必守住）**：升级命令**只动 skill 文件**，**绝不**重命名、移动或改写 `doc-framework/` 文档根与 `AGENTS.md`；被本地定制过的 skill 目录会自动跳过。**升级后旧文档不迁移也能照常跑**（解析器不认章节编号，旧格式计划按旧行为处理），"想用上新模型"才需要第 4 步的人工对齐。

### 第 3 步：核验框架已升级

- 逐文件看 `.agents/skills/.doc-framework.json` 的 `version` 是否已是 `v<package.json 的 version>`（marker 的 `version` 就是 `v${package.json.version}`，**不是** tag 名，两者不同时以 marker 里的值为准）；若报"跳过（本地已定制）"，把该目录的定制内容列给用户决定（要放弃定制就用 `pnpm rebuild doc-framework`，它无条件先删后拷）；
- **升级后必须新开一个会话**，新 skill 才会被加载——同一会话里"升级 + 用新流程"是无效的（旧 skill 的内容已在上下文里）；
- 再跑一次 `check`，确认没有出现新的硬失败；报告里要区分**升级带来的新提示**（哨兵 R4、契约 §9 回链 R3）与原有问题。

### 第 4 步：文档体系人工迁移（**动用户资产，逐批确认**）

先回答/确认一个前置问题：**这个项目是不是英文文档根？**（`doc-framework-en/`，或历史名 `docs-framework/`）
- **不是** → 中文根项目**无需任何动作**，旧中文规范名、历史英文枚举（`merged`/`n/a`）、混排目录名（`modules/…/plans/`）仍被当作**数据兼容别名**识别；
- **是** → 必须迁移（命令不会代做）：① `mv doc-framework-en doc-framework`；② 目录名/文件名/章节名/头部字段/枚举值按框架 README「产物命名表」改回中文（`profile.md`→`项目档案.md`、`modules/`→`模块/`、`## 5. Application footprint`→`## 5. 应用落点`、`> Status:`→`> 状态：` 等）；③ 契约 §9 来源列与「合并状态」值改中文；④ 同步 `AGENTS.md` 里的路径与命名描述。

然后按下面的**优先级**逐项做，**每批改完停下来让用户确认再继续**：

> **P0 只对"契约模型改造（v2.2）之前"的旧项目成立**：判定看第 1 步勘察结果——**`AGENTS.md` 纪律段已是"语义增量 + `/module-doc` 合并"写法、契约 §9 来源列已是四值**，说明该项目已是新模型，P0 只需抽查一致性，不必重写。**类别判据见文末「判断你的项目属于哪一类」。**

#### P0 必改（不改 ⇒ 新会话里 AI 仍按旧模型工作）

1. **`AGENTS.md` 的「编码纪律」段**对齐 `templates/AGENTS.md.tpl`：核心是「**语义变更写进计划的「语义增量」节**（批准计划 = 语义定稿）→ 实施 → 由 `/module-doc` 的合并增量把增量合并进契约正文与 `接口.md`」。旧写法（语义直接写契约正文 / 契约先行 / 在契约里登记待实现语义）**必须删掉**——留着就是两套模型打架。顺带对齐同一份模板里的：文档根与命名固定中文、一级章号阿拉伯数字、模块三态（待实现 / 存量已建档 / 存量未建档）、三通道与形态（完整 / 轻量 / 直改）。
2. **每份模块契约的 §9「变更记录」**对齐新模板：
   - 来源枚举扩为 `需求 / 代码 / 实现 / 合并`；删除"契约定稿登记"一类旧来源写法；
   - 新增行改为「**结论 + 理由一句话 + 回链凭据**」，实施细节（类名/方法/行号/SQL 片段/取证过程）不抄；
   - 回链凭据用**不会消失的**：`计划标识 @提交SHA` / `@提交SHA` / `需求#编号`（旧写法指向计划文件路径仍被识别，计划被清理后只提示）；
   - **存量行不必回填**：`check` 只对 `合并`/`实现` 行的空凭据硬报错，`需求`/`代码` 的旧批量登记行只计数提示。

#### P1 建议改（低成本、收益明确）

3. **归档目录改名**：`git mv 计划/archive 计划/归档`（模块级同理 `模块/{名}/计划/archive → 模块/{名}/计划/归档`），并同步 `AGENTS.md` 里的路径描述。识别层认中英并集，**不改也不会产生"归档计划被当成在途计划"的误判**，但同一文档根内应保持单一语言。

#### P2 可选（纯一致性 / 防漂移，不做不报错）

4. **一级章号统一阿拉伯数字**："`## 一、标题`" → "`## 1. 标题`"，并把正文里的 `§三/§四/§六` 交叉引用改成 `§3/§4/§6`。范围：四份全局文档（总契约 §1–§8 / 测试规范 §1–§6 / 接口规范 §1–§5 / 项目档案）、计划模板 §0–§11（「语义增量」「建模补充」**不编号**，是解析锚点）、类型层 §0–§5、应用层 §1–§6、边界文档 §1–§5、探索记录 §1–§5、模块测试文档 §1–§10。解析器不认编号，**漏改只影响人读，不报错**。
5. **四份全局文档的单一职责**：① 档案「通用约定」节首补一句唯一真相声明（字段名与取值的唯一出处）；② 类型层规范 `## 4.` 删掉 `del_flag 0/2`、`pageNum/pageSize` 之类**取值复制**，改为回链档案；③ 接口规范不再承载"维护流程"段（归总契约 §7）；④ 契约 §4 节首补越界判据。

#### 顺手对齐（迁移过程中自然发生）

6. **哨兵**：凡是这次改到的全局文档 / 计划模板 / 契约，在首行补上
   `<!-- doc-framework:docstruct v<框架版本> | 全局文档结构版本；… -->`——**照抄框架模板该行原文，只把 `{{框架版本}}` 换成开工时读到的 `package.json` version（前面加 `v`）**，说明文字一个字都不要改写。
   **哨兵落后于框架版本会让 `check` 失败（⚠️）**；**完全没有哨兵（v2.4.0 之前的初始化）只是一条 ℹ️，不影响退出码**——体系不逼人重写历史文档，改到哪份补哪份即可。

### 第 5 步：验收（必须做）

1. `npx doc-framework check` 全绿（ℹ️ 提示不影响退出码，但要逐条解释给用户）；
2. 哨兵比对：已迁移的文档声明的结构版本 == `v<package.json 的 version>`（**不是 tag 名**；两个值不一致时，以框架仓库 `package.json` 为准）；
3. `.agents/skills/.doc-framework.json` 的 `version == v<package.json 的 version>`，且没有"本地已定制"的意外跳过；
4. P0 两项（AGENTS.md 纪律段 / 契约 §9）逐模块确认到位；
5. 出**验收报告**：基线 check 输出 vs 现在的输出（差异逐行说明）、已迁移项、**未迁移的可选项 + 不做会怎样**、以及"需要用户手动决定"的遗留项（例如要不要清理归档计划——**归档不删文件是纪律，清理由是人的决定**）。

### 硬性禁止（越界即停下来问）

1. **不自动迁移文档结构**：不许在没有用户逐批确认的情况下批量重写契约 / 总契约 / 计划；不许顺手"美化"没被要求的章节。
2. **不删任何文档**：计划归档只做"校验 §9 已登记 → 写提交 SHA → `git mv` 进 `计划/归档/`"；是否清理由人手动 `git rm` 决定。
3. **不擅自改依赖与 CI**：除第 2 步那一个版本号，其他依赖 / 脚本 / CI 配置不动。
4. **不在框架仓库里新建 / 移动 / 删除 tag**，也不"顺手"改 `package.json` 的版本让 tag 与版本对上——发版是人的动作，你只**读**版本信息。
5. **不把框架仓库的模板整份覆盖进项目**：项目里的档案与契约是**项目自有资产**，只做"对齐"，不做"回灌"；模板只用来读目标形态。
6. 拿不准的项**列成待决清单交给用户**，不要自己拍板——尤其是"不动也能跑"的 P2 项。

### 判断你的项目属于哪一类

- 有 `doc-framework-en/` 或 `docs-framework/` → 必须迁移（唯一"强制"项）。
- 中文 `doc-framework/`，且 skill 版本早于 v2.2（`merged`/`n/a` 一类英文枚举、契约里直接写待实现语义） → P0 两项必改，其余可选。
- 中文 `doc-framework/`，skill 已是 v2.2 及以后（契约已是"已生效真相"模型，只是缺少 P1/P2 的对齐） → 只升框架 + 新开会话即可，文档按 P1/P2 自愿对齐。

1. **升完框架但没改 `AGENTS.md`** —— skill 是新的、总纲是旧的，新会话里 AI 会按旧模型写契约，且不报错。
2. **在升级前的同一个会话里继续用新流程** —— 旧 skill 内容仍在上下文，等于没升级；升级后必须新开会话。
