# 老项目升级 doc-framework —— 交给 AI 的上下文

> **怎么用**：在**老项目**（要升级的那个项目）里新开一个 AI 会话，把下面「===== 可粘贴上下文开始/结束 =====」之间的内容**整段粘贴**即可，无需任何准备——目标版本按 GitHub tag 现场解析。AI 会先解析最新 tag、做只读勘察、给出差异报告，等你确认后才动手。
>
> 这份文件是给**使用者**的升级操作包，不是框架仓库的开发文档。**迁移动作以本文件第 4 步为唯一权威**；升级机制见 `docs/设计文档.md` §9.3，关键决策见 §12.1。
>
> **不写死版本目标**：升级目标 = **GitHub 仓库的最新 tag**，由 AI 在执行时解析。本文件里出现的版本号只用于说明"某个约定是从哪一版开始的"。

## 任务：把本项目的 doc-framework 从旧版本升级到 GitHub 最新 tag

本项目在早期用 doc-framework 初始化过（项目根有 `doc-framework/` 文档根与 `AGENTS.md` 引导段），现在要升级到**最新 tag**。v3 起安装只有一个 CLI 入口 **`doc-framework install`**，取包走 **GitHub tag**（没有 npm 发布、没有 `install.sh`、没有 `postinstall`）。

> **版本口径（先看这条，后面全用它）**：升级目标 = GitHub 仓库的最新 tag（形如 `v3.0.1`），不是某个写死的版本，也**不是 npm 包**。你**开工第一件事**就是把它解析成具体值，之后每一步提到的 `<目标版本>` 都指这个 tag：
>
> ```bash
> git ls-remote --tags --refs https://github.com/knight-peter/doc-framework.git 'v*' \
>   | sed 's|.*refs/tags/||' | sort -V | tail -1
> # 例：v3.0.1 ⇒ <目标版本>
> npx --yes "github:knight-peter/doc-framework#<目标版本>" --help
> ```
>
> 钉版本用同一个 tag：`"doc-framework": "github:knight-peter/doc-framework#<目标版本>"`；文档结构哨兵写 **`v` + `package.json` 的 version**（tag 去掉前导 `v` 应与之一致）。版本在安装后从 `node_modules/doc-framework/package.json` 读；未装依赖时从临时 clone 的同 tag 目录读。

### 第 0 步：先读官方源这三处，不要凭记忆干活

1. `node_modules/doc-framework/README.md` 的「安装」「升级」「文档体系」三节；
2. `node_modules/doc-framework/docs/设计文档.md` **§9.3「升级的作用域与迁移」**——讲升级机制与机检检查点；**本文件第 4 步才是迁移动作的唯一清单**。若项目本地没有 `node_modules`，把目标 tag 临时 clone 到 `/tmp` 读（用后即弃）：
   ```bash
   git clone --depth 1 --branch <目标版本> \
     https://github.com/knight-peter/doc-framework.git /tmp/doc-framework-<目标版本>
   ```
3. `node_modules/doc-framework/templates/AGENTS.md.tpl` 与 `templates/模块/{模块名}/契约.md.tpl`（**§8.2 关键验收场景 + §9 指针节**）——新模型的**目标形态**长这样；没有 node_modules 时用 `npx --yes "github:knight-peter/doc-framework#<目标版本>" template AGENTS` / `template 契约`（或读上一步 clone 的 `templates/`）。

### 第 2 步：升框架（机器动作，安全）

v3 只有一个 CLI 入口：**`doc-framework install`**，取包走 **GitHub tag**。按项目现状二选一：

- **原来就是 git 依赖**：把 `package.json` 里的 `doc-framework` 改成 `"github:knight-peter/doc-framework#<目标版本>"` → `npm install`（或 `pnpm install`）→ `npx doc-framework install`（pnpm 项目 `pnpm exec doc-framework install`）。**不要再配 `onlyBuiltDependencies`**（已无 postinstall）。
- **原来是 install.sh 脚本安装**：安装 Node ≥22 → 在项目根跑 `npx --yes "github:knight-peter/doc-framework#<目标版本>" install`；项目不需要 package.json。

> 若只想升级 skill、不改依赖：`npx --yes "github:knight-peter/doc-framework#<目标版本>" sync`（安全：本地定制跳过）；`install` 是强制刷新（会覆盖定制 skill，但**不动文档与 AGENTS 永久段**）。

**这一步的边界（务必守住）**：安装/升级命令**只动 skill 文件**，**绝不**重命名、移动或改写 `doc-framework/` 文档根与 `AGENTS.md`；被本地定制过的 skill 会被 `sync` 跳过。**升完 skill 只是第一步——文档体系必须走第 4 步人工迁移**。

### 第 3 步：核验框架已升级

- 看 `.agents/skills/.doc-framework.json`：每个 skill 的 `skills[名称].version` 是否已是 `v<package.json 的 version>`；若 `sync` 报"跳过（本地已定制）"，把该 skill 的定制内容列给用户决定（要放弃定制就用 `npx --yes "github:knight-peter/doc-framework#<目标版本>" install`，它无条件先删后拷）；
- **升级后必须新开一个会话**，新 skill 才会被加载——同一会话里"升级 + 用新流程"是无效的；
- 再跑一次 `check`，区分**升级带来的新提示**（哨兵 R4、文档落后检查、规范层归属判据）与原有问题；升级后首次 `check` 对存量应用规范报出的一波规范层 ℹ️ 是迁移指引，不是错误。

### 第 4 步：文档体系人工迁移（**动用户资产，逐批确认**）

先确认前置问题：**这个项目是不是英文文档根？**（`doc-framework-en/`，或历史名 `docs-framework/`）

- **不是** → 命名不用改，直接做下面的批次；
- **是** → **必须迁移**（命令不会代做）：① `mv doc-framework-en doc-framework`；② 目录名 / 文件名 / 章节名 / 头部字段 / 枚举值按框架 README「文档体系」树与设计文档 §8.1 改回中文（`profile.md`→`项目档案.md`、`modules/`→`模块/`、`## 5. Application footprint`→`## 5. 应用落点`、`> Status:`→`> 状态：` 等）；③ 「合并状态」值改中文；④ 同步 `AGENTS.md` 的路径与命名描述。

**版本 → 批次索引**（只决定"从哪批开始"，所有项目一律迁到最新）：

| 项目现状 | 先做 |
|---|---|

| v2.3 | P1-3（归档目录改名） |

按下面**批次**逐项做（**每批改完停下来让用户确认再继续**）：

#### P0 必改（不改 ⇒ 新会话里 AI 仍按旧模型工作）

1. **`AGENTS.md` 的「编码纪律」段**对齐 `templates/AGENTS.md.tpl`：核心是「**语义变更写进计划的「语义增量」节**（批准计划 = 语义定稿）→ 实施 → 由 `/module-doc` 的合并增量把增量合并进契约正文与 `接口.md`」。旧写法（语义直接写契约正文 / 契约先行 / 在契约里登记待实现语义）**必须删掉**。顺带对齐：文档根与命名固定中文、一级章号阿拉伯数字、模块三态、三通道与形态（完整 / 轻量 / 直改）。
2. **每份模块契约的 §9「变更记录」整表删除**，替换为新模板的两行指针：
   > 本模块的变更历史不在本文件：语义与实现的历史看 git 提交；决策与被否方案看**探索记录**（`{文档根}/探索/`）。本契约只记当前真相（应然 ≡ 实然）。
   - 旧表历史在 `git log -p 契约.md` 里，**删除不丢信息**；§9 章号保留（§10 生产 SQL 登记不重编号）；
   - 这次删除提交会天然把"文档落后检查"的基线推进到当下——**建议按模块一次性迁完**；
   - 契约头部可补一行 `建档方式：代码对账 / 需求建模`（可选）；
   - 追溯凭据改放**提交信息 trailer**：`模块:{模块名}` / `计划:{计划标识}`（直改写 `计划:无`）/ `契约:无需变更`，格式权威见 `AGENTS.md.tpl` §5。

#### P1 命名与路径（低成本、收益明确）

3. **归档目录改名**：`git mv 计划/archive 计划/归档`（模块级同理），并同步 `AGENTS.md` 里的路径描述——同一文档根内只保留一种命名。

#### P2 一致性（不改不影响解析，但对齐到最新要做完）

4. **一级章号统一阿拉伯数字**：`## 一、标题` → `## 1. 标题`，正文 `§三/§四/§六` → `§3/§4/§6`。范围：四份全局文档、计划模板、类型层、应用层、边界文档、探索记录、模块测试文档。解析器不认编号，这一步不影响功能。
5. **单一职责收敛**：
   - 档案「通用约定」节首补唯一真相声明；
   - 类型层规范删 `del_flag 0/2`、`pageNum/pageSize` 等**取值复制**，改回链档案；
   - 接口规范不再承载"维护流程"段（归总契约 §7）；
   - 契约 §4 节首补越界判据；
   - **测试文档去重**：`测试.md` §6 删断言块（改回链契约 §8.2 SC-n）、§8 只留本模块实例、§10 只留取值表；`测试规范.md` §3/§3.3 补唯一归属声明、§4 的 SQL 占位符改 `{…}` 记法；
   - **契约措辞**：§8.2 标题 `验收标准` → **`关键验收场景`**；§9 抬头看**探索记录**；§10 抬头补"只登记执行环境含生产 SQL"。
6. **计划模板结构（v2.9.0 / v2.10.0）**：
   - 计划正文只呈现最新方案：删 `0 修订记录` / `关键设计决策` / `里程碑` / `回写清单` 四节；被否理由归探索记录，历史归 git；
   - §1 统一为「需求与思路」（1.1 需求 / 1.2 实施后结果 / 1.3 思路〔图唯一落点〕/ 1.4 不做什么）；轻量形态同样有 §1 压缩版；
   - §3 是**授权白名单**，不是变更记录；SQL 表补 `执行环境` 列（`生产+开发` / `仅开发`），只有含生产的行登记契约 §10；
   - 任务清单：勾选框只留给 AI 可验证任务；人工/平台步骤写成**不带勾选框**的登记行 `- 5.2 【人工·{执行方}】{动作}`；测试任务不写（归 `/module-test`）；
   - 图统一画在 §1.3，图前粗体标注角色：`状态机` / `页面结构 · 端名` / 不标＝仅说明；
   - 旧计划无需迁移：解析器按标题关键词读，缺 §1、多出已删节都不报错；在途首建计划把图挪到 §1.3 即可。

#### P3 规范层（按 `check` 的规范层 ℹ️ 提示逐项做——那波提示就是清单）

7. **应用规范四不写清理**：删变更痕迹（版本号/日期/`来源=`/修订沿革）、代码清单（回链路径）、缺口待办（→ 计划）；「禁止 X」的否定性结论要留。
8. **跨应用共享约定上移 `边界/`**：两个及以上应用规范出现的同主题约定 → `边界/{能力}边界.md`，应用规范只留本端机制。
9. **深度主题拆分册**：单节 >80 行或小节数 >8 的应用规范，把深度主题拆到 `规范/{应用标识}-{主题}.md`，并在应用规范 §3.1 索引登记（`check` 机检索引 ↔ 分册一致）。
10. **应用规范 §6「技术栈特有检查项」删除**：检查项并入各分册的检查项节。

#### 顺手对齐（迁移过程中自然发生）

11. **哨兵**：这次改到的全局文档 / 计划模板 / 契约，在首行补
    `<!-- doc-framework:docstruct v<框架版本> | 全局文档结构版本；… -->`——照抄框架模板该行原文，只把 `{{框架版本}}` 换成开工时读到的 `package.json` version（前面加 `v`）。说明文字一个字都不要改写。**哨兵落后于框架版本会让 `check` 失败（⚠️）**；**完全没有哨兵**（v2.4.0 之前）只给一条 ℹ️，但按最新规范要补齐——迁移时改到哪份补哪份。`check` 的 R4 只校验四份全局文档 + 在途计划；模块契约哨兵是声明性标记，不逐模块比版本。

### 第 5 步：验收（必须做）

1. `check` 全绿（有依赖 `npx doc-framework check`；无依赖用第 0 步的 GitHub 前缀）；ℹ️ 提示不影响退出码，但要逐条解释。
2. 哨兵比对：已迁移文档的结构版本 == `v<package.json 的 version>`（从 `node_modules/doc-framework/package.json` 或临时 clone 的 `package.json` 读）。
3. `.agents/skills/.doc-framework.json` 的 `version == v<package.json 的 version>`，且没有"本地已定制"的意外跳过。
4. P0 两项（AGENTS.md 纪律段 / 契约 §9）逐模块确认到位。
5. 出**验收报告**：基线 check 输出 vs 现在的输出（差异逐行说明）、已迁移项、**未完成项 + 卡在哪**、以及"需要用户手动决定"的遗留项（例如要不要清理归档计划——**归档不删文件是纪律，清理由是人的决定**）。

### 硬性禁止（越界即停下来问）

1. **不自动迁移文档结构**：不许在没有用户逐批确认的情况下批量重写契约 / 总契约 / 计划；不许顺手"美化"没被要求的章节。
2. **不删任何文档**：计划归档只做"校验 `合并状态=已合并` 且契约已承接 → `git mv` 进 `计划/归档/`"；是否清理由人手动决定。（例外：P0-2 明确要求的**契约 §9 旧表整表删除**——历史在 `git log -p` 里，不算丢文档。）
3. **不擅自改依赖与 CI**：除第 2 步那一个依赖 tag，其他依赖 / 脚本 / CI 配置不动。
4. **不在框架上游新建 / 移动 / 删除 tag**，也不"顺手"改官方 `package.json` 的版本——发版是人的动作，你只**读** GitHub tag 与 `package.json` 版本信息。
5. **不把官方模板整份覆盖进项目**：项目里的档案与契约是**项目自有资产**，只做"对齐"，不做"回灌"；模板只用来读目标形态。
6. 拿不准的项**列成待决清单交给用户**，不要自己拍板——尤其是 P3 里需要逐条裁决的内容项（哪些是跨应用共享约定、哪些该拆册）。
