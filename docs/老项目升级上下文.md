## 任务：把本项目的 doc-framework 从旧版本升级到框架仓库的最新 tag

本项目在早期用 doc-framework 初始化过（项目根有 `doc-framework/` 文档根与 `AGENTS.md` 引导段），现在要升级到框架的**最新已发布版本**。老项目升级 = 照原来的安装方式升到最新（第 2 步）：npm 方式的项目官方源一律用 `node_modules/doc-framework/`（skills / templates / scripts / package.json 都在里面），脚本方式的项目重跑安装脚本即可——**不要去找本地的框架仓库检出**。

> **版本口径（先看这条，后面全用它）**：**升级目标 = 框架仓库的最新 tag，不是某个写死的版本号**。本提示词不写死版本；你**开工第一件事**就是把它解析成具体值，之后每一步提到的 `<目标版本>` 都用它：
>
> ```bash
> # 从本项目 package.json 读出依赖里的 git 地址，直接列远端 tag——不需要任何本地检出
> REPO=$(node -p "require('./package.json').dependencies['doc-framework'].replace(/#.*$/,'')")
> git ls-remote --tags "$REPO" | sed 's|.*refs/tags/||' | grep -v '\^{}' | sort -V | tail -1   # 最新 tag ⇒ <目标版本>，形如 v2.7.0
> ```
>
> （脚本方式安装、没有 npm 依赖的项目：直接问用户要目标 tag，或 `git ls-remote --tags https://github.com/knight-peter/doc-framework.git` 自己解析。）
>
> 两个值得**各用其位**：钉依赖用 **tag**（`#<目标版本>`）；文档结构**哨兵**写 **`package.json` 的 version**（前面加 `v`）——哨兵要与代码里的版本一致，否则 `check` 的 R4 会误判。version 在第 2 步安装后从 `node_modules/doc-framework/package.json` 读（就是项目里实际跑的那份）。两者不一致是**正常可能发生**的情况（历史上 `package.json` 曾长期领先最新 tag：一度写到 2.6.0 而最新 tag 还停在 v2.4.0），**遇到不要"纠正"任何一方，也不要自作主张新建 / 移动 tag**（发版是人的动作），按上面各用其位即可。
>
> 顺便把结果写进第 1 步的差异报告（表里已留「目标版本」一行）：**项目现状版本 → 目标版本**。

### 第 2 步：升框架（机器动作，安全）

按本项目原来的安装方式二选一：

- **npm/pnpm git 依赖**：把 `package.json` 里的 `git+https://github.com/knight-peter/doc-framework.git#<旧版本>` 改成 `#<目标版本>`（= 开工时解析出的最新 tag）→ `pnpm install`（lockfile 锁死时用 `pnpm update doc-framework`；若 store 复用跳过了 postinstall，用 `pnpm rebuild doc-framework`）。
- **一键脚本**：重跑安装脚本。

> 若本项目只想要最新 skill 而不改依赖：`npx doc-framework sync`（等价物）。

**这一步的边界（框架纪律，务必守住）**：升级命令**只动 skill 文件**，**绝不**重命名、移动或改写 `doc-framework/` 文档根与 `AGENTS.md`；被本地定制过的 skill 目录会自动跳过。**所以升完 skill 只是第一步——文档体系必须走第 4 步人工迁移**：体系不兼容旧结构，没有"留在旧结构也能用"这条路。

9. **应用规范 §6「技术栈特有检查项」删除**：检查项并入各分册的检查项节（消除 §3↔§6 的双写）。

#### 顺手对齐（迁移过程中自然发生）

10. **哨兵**：凡是这次改到的全局文档 / 计划模板 / 契约，在首行补上
   `<!-- doc-framework:docstruct v<框架版本> | 全局文档结构版本；… -->`——**照抄框架模板该行原文，只把 `{{框架版本}}` 换成开工时读到的 `package.json` version（前面加 `v`）**，说明文字一个字都不要改写。
   **哨兵落后于框架版本会让 `check` 失败（⚠️）**；**完全没有哨兵**（v2.4.0 之前的初始化）`check` 只给一条 ℹ️，但按最新规范**要补齐**——迁移时改到哪份补哪份。（`check` 的 R4 只校验**四份全局文档 + 在途计划**；**模块契约的哨兵是声明性标记**，补齐即可、不进退出码——逐模块比结构版本属未启用能力，见设计文档 §6.3 ①A。）

### 第 5 步：验收（必须做）

1. `npx doc-framework check` 全绿（ℹ️ 提示不影响退出码，但要逐条解释给用户）；
2. 哨兵比对：已迁移的文档声明的结构版本 == `v<package.json 的 version>`（**不是 tag 名**；从 `node_modules/doc-framework/package.json` 读——它是项目里实际跑的那份）；
3. `.agents/skills/.doc-framework.json` 的 `version == v<package.json 的 version>`，且没有"本地已定制"的意外跳过；
4. P0 两项（AGENTS.md 纪律段 / 契约 §9）逐模块确认到位；
5. 出**验收报告**：基线 check 输出 vs 现在的输出（差异逐行说明）、已迁移项、**未完成项 + 卡在哪**、以及"需要用户手动决定"的遗留项（例如要不要清理归档计划——**归档不删文件是纪律，清理由是人的决定**）。

### 硬性禁止（越界即停下来问）

1. **不自动迁移文档结构**：不许在没有用户逐批确认的情况下批量重写契约 / 总契约 / 计划；不许顺手"美化"没被要求的章节。
2. **不删任何文档**：计划归档只做"校验 `合并状态=已合并` 且契约已承接 → `git mv` 进 `计划/归档/`"；是否清理由人手动 `git rm` 决定。（例外：本提示词 P0-2 明确要求的**契约 §9 旧表整表删除**——它的历史在 `git log -p` 里，不算丢文档。）
3. **不擅自改依赖与 CI**：除第 2 步那一个版本号，其他依赖 / 脚本 / CI 配置不动。
4. **不在框架上游新建 / 移动 / 删除 tag**，也不"顺手"改官方 `package.json` 的版本让 tag 与版本对上——发版是人的动作，你只**读**版本信息。
5. **不把官方模板整份覆盖进项目**：项目里的档案与契约是**项目自有资产**，只做"对齐"，不做"回灌"；模板只用来读目标形态。
6. 拿不准的项**列成待决清单交给用户**，不要自己拍板——尤其是 P3 里需要逐条裁决的内容项（哪些是跨应用共享约定、哪些该拆册）。

### 判断你的项目属于哪一类

**分类只决定"从哪一批开始做"，不决定"做不做"**——一律迁到最新：

- 有 `doc-framework-en/` / `docs-framework/` → 先做英文根迁移（第 4 步「是」分支），再做 P0–P3；
- 中文根 + skill 版本早于 v2.2（`merged` / `n/a` 一类英文枚举、契约里直接写待实现语义）→ **从 P0-1 开始**（旧模型不改，新会话里 AI 仍按旧模型工作）；
- 中文根 + skill 已是 v2.2 及以后 → P0-1 抽查即可，**P0-2 起逐批做完**（重点通常是 P0-2 的 §9 删表与 P3 规范层）。

### 两个最容易踩的坑

1. **升完框架但没改 `AGENTS.md`** —— skill 是新的、总纲是旧的，新会话里 AI 会按旧模型写契约，且不报错。
2. **在升级前的同一个会话里继续用新流程** —— 旧 skill 内容仍在上下文，等于没升级；升级后必须新开会话。
