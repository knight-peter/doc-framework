# 老项目升级 doc-framework —— 交给 AI 的上下文

> **怎么用**：在要升级的**老项目**里新开一个 AI 会话，把「===== 可粘贴上下文开始/结束 =====」之间整段粘贴。AI 会先解析最新 tag → 只读勘察 → 差异报告，确认后才动手。
> 给**使用者**的升级操作包，不是框架开发文档。**迁移动作以第 4 步为唯一权威**；升级机制见 `docs/设计文档.md` §9.3。**不写死版本**：目标 = GitHub 最新 tag，执行时解析。

## 任务：把本项目的 doc-framework 升级到当前版本

本项目用 doc-framework 初始化过（项目根有 `doc-framework/` 文档根与 `AGENTS.md` 引导段），现在对齐到**当前版本（4.1.x）**。安装与升级只有一个 CLI 入口 **`doc-framework install`**，取包走 **GitHub tag**（没有 npm 发布、没有 `install.sh`、没有 `postinstall`）。

**版本口径**（开工第一件事，之后每一步的 `<目标版本>` 都指它）：

```bash
git ls-remote --tags --refs https://github.com/knight-peter/doc-framework.git 'v*' \
  | sed 's|.*refs/tags/||' | sort -V | tail -1      # 例：vX.Y.Z
```

- 钉依赖用同一 tag：`"doc-framework": "github:knight-peter/doc-framework#<目标版本>"`；
- 哨兵与 skill marker 的 `version` 都写 **`v` + `package.json` 的 version**（tag 去掉前导 `v` 应一致），从 `node_modules/doc-framework/package.json` 读；未装依赖时读临时 clone 的同 tag 目录。

### 第 0 步：先读官方源，不凭记忆干活

- 目标包 README 的「安装」「升级」「文档体系」三节；
- 同包 `docs/设计文档.md` §9.3——升级机制与作用域；
- 同包 `templates/AGENTS.md.tpl`、`templates/总契约.md.tpl`、`templates/能力/{能力}契约.md.tpl`——**目标形态**。

没有 `node_modules` 时用临时 clone（用后即弃），或直接用 CLI 取模板：

```bash
git clone --depth 1 --branch <目标版本> \
  https://github.com/knight-peter/doc-framework.git /tmp/doc-framework-<目标版本>
npx --yes "github:knight-peter/doc-framework#<目标版本>" template AGENTS   # 或 template 契约
```

### 第 1 步：只读勘察，产出差异报告（本步不写任何文件）

按 **项 / 现状 / 目标 / 必改或可选 / 影响面（文件数）** 成表，并写清「**现状版本 → 目标版本**」：

| 探什么 | 目标形态 / 判据 |
|---|---|
| 现状版本 | `.agents/skills/.doc-framework.json` 的 `version`（skill 目录可能在 `.claude/skills` / `.cursor/skills`） |
| skill 本地定制 | marker 的 `skills[名称]` 逐文件 sha256 对比官方 `skills/`；**单个 skill** 下任一文件不一致即该 skill 定制，其它不受影响 |
| `AGENTS.md` 纪律段 | 应写「语义变更写进计划的「语义增量」节，实施后由 `/module-doc` 合并进契约」；只写"契约先行"即旧形态，必改 |
| 契约形态 | 9 章：§8 只留指针（SC 在 `测试/验收.md`）；§9 = 生产 SQL；无变更记录章；`<!-- contract-schema: 4 -->` |
| 能力契约 | 目录 `能力/`、文件 `{能力}契约.md`、标记 `<!-- capability-schema: 3 -->`；出现 `边界/`、`boundary-schema`、`## N. 验收` 即待迁移 |
| 文档结构哨兵 | 四份全局文档、模块契约、计划首行的 `<!-- doc-framework:docstruct vX.Y.Z … -->`；缺失即待补 |
| 目录与章号 | 归档目录为 `计划/归档/`（非 `archive/`）；一级章号为 `## N. 标题`，无 `## 三、` 与正文 `§三` 引用 |
| 总契约模块表 | §4 应为**一张按模块的表**（含「依赖的下游模块/数据」与「能力依赖」列）；§5 只放全景图 |
| 总契约规则章 | 不应有旧的 `§7 维护规则` / `§8 使用流程`；§7 是**能力契约索引表**（能力→契约→主责→消费者） |
| 测试资产 | `模块/*/测试/验收.md` 只放 SC；`方案.md` 做索引；`{主题}_测试.md` 只放用例；`报告/` 不参与文档校验 |
| 计划模板 | 无 `0 修订记录` / `关键设计决策` / `里程碑` / `回写清单`；图在 §1.3；人工步骤为无勾选框登记行 |
| 应用规范 | 无 `## 7.` 及以后小节、版本号/日期/`来源=` 内联、按模块罗列差异、跨应用重复主题 |
| 英文文档根 | 有 `doc-framework-en/` 或历史名 `docs-framework/` → **必须人工迁移**（命令不探测这两个名字） |
| 版本基线 | 项目根跑 `check`（有依赖 `npx doc-framework check`，无依赖用 GitHub 前缀），留完整输出（`--json` 亦可）作升级后对照 |

### 第 2 步：升框架（机器动作，安全）

- **原有 git 依赖**：`package.json` 的 `doc-framework` 改成 `"github:knight-peter/doc-framework#<目标版本>"` → `npm install`（或 `pnpm install`）→ `npx doc-framework install`（pnpm 项目 `pnpm exec`）。
- **原先用 `install.sh`**：装 Node ≥22 → 项目根跑 `npx --yes "github:knight-peter/doc-framework#<目标版本>" install`；不需要 `package.json`。
- 只升 skill、不动依赖：`npx --yes "github:knight-peter/doc-framework#<目标版本>" sync`；`install` 是强制刷新（覆盖定制 skill，但**不动文档与 AGENTS 永久段**）。

**边界**：这些命令**只动 skill 文件**，绝不重命名、移动或改写 `doc-framework/` 文档根与 `AGENTS.md`。升完 skill 只是第一步，**文档体系必须走第 4 步人工迁移**。

### 第 3 步：核验框架已升级

- marker 里每个 `skills[名称].version` 是否已是 `v<package.json 的 version>`；有"跳过（本地已定制）"就把该 skill 的定制内容列给用户决定（放弃定制用 `install`）；
- **必须新开一个会话**，新 skill 才会加载——同一会话里"升级 + 用新流程"无效；
- 再跑一次 `check`，区分**升级带来的新提示**与原有问题；升级后首次 `check` 的规范层 ℹ️ 是迁移指引，不是错误。

### 第 4 步：文档体系人工迁移（**动用户资产，逐批确认**）

先答一个问题：**是不是英文文档根？**（`doc-framework-en/` 或历史名 `docs-framework/`）

- **不是** → 直接做批次；
- **是** → **必须迁移**（命令不代做）：① `mv doc-framework-en doc-framework`；② 目录名/文件名/章节名/头部字段/枚举值按 README「文档体系」树改中文；③「合并状态」值改中文；④ 同步 `AGENTS.md` 的路径与命名。

**先判断起点版本**：

- **现状 < 4.0.0**：先完成 4.0.0 前置迁移（只做一次，之后不再回头）：
  1. 每份契约补所有权声明，§7 只留 `INV-{模块名}-NN`（`TRAP-*` 退场）；
  2. 测试资产迁入 `模块/{模块名}/测试/`（`验收.md` = SC 唯一事实源、`方案.md`、`{主题}_测试.md`、`报告/`）；
  3. 契约改 9 章（§8 指针、§9 生产 SQL），标 `<!-- contract-schema: 4 -->`；
  4. 总契约 §4 合成一张模块表（删 §5.1 矩阵），跑 `doc-framework migrate v5 --dry-run` 按清单执行。
- **现状 = 4.0.0**：直接做 4.1.0 迁移。

#### 4.1.0 迁移：能力契约单命名 + schema3

> `边界/` → `能力/`、`{能力}边界.md` → `{能力}契约.md`；能力契约只保留 §1 人读层 / §2 统一约定 / §3 接入 Checklist / §4 常见陷阱 / §5 失败模式 / §6 关联代码。**先迁移再 check**（旧目录 `边界/` 会让 `check` 直接报 ❌）。命令：`doc-framework migrate v6 --dry-run`。

1. **目录**：`git mv 边界 能力`；`{能力}边界.md` 逐份改为 `{能力}契约.md`。
2. **标记**：`<!-- boundary-schema: … -->` → `<!-- capability-schema: 3 -->`。
3. **内容**：删 `## 6. 验收归属`（验收链：契约主责 → 主责模块契约 §8 → `测试/验收.md`）；`## 7. 关联代码` → `## 6`；§1 删消费者表，改为「是什么 / 为什么需要 / 不做什么 / 谁在用（≤800B）」。
4. **引用回写**：契约头部「委托给 / 关联文档」、`总契约 §7` 契约列、计划、应用规范中的 `边界/` → `能力/`；`总契约 §4` 列名「边界依赖」→「能力依赖」。
5. **消费者**：清单只留 `总契约 §7`；主责两处必须一致（`check` 机检）。
6. **验收**：`check` 无旧目录报错、无 schema3 硬错误；`audit` 显示 `schema 3`。

#### 其余对齐（按勘察命中项做）

1. **AGENTS.md** 对齐 `templates/AGENTS.md.tpl`；归档目录统一 `计划/归档/`；一级章号阿拉伯数字。
2. **总契约**：只保留一张模块表；§7 为能力契约索引；删除旧 §7 维护规则 / §8 使用流程。
3. **应用规范**：删变更痕迹、代码清单、缺口待办；跨应用共享约定上移 `能力/`；深度主题拆 `规范/{应用}-{主题}.md` 并登记 §3.1 索引；删 §6「技术栈特有检查项」。
4. **计划**：只留最新方案；§1 统一为「需求与思路」；§3 是授权白名单；SQL 标 `执行环境`；人工步骤无勾选框；图统一 §1.3。
5. **哨兵**：改到的全局文档 / 计划模板 / 契约补 `<!-- doc-framework:docstruct v<package.json version> … -->`（照抄模板）。

### 第 5 步：验收（必须做）

1. `check` 全绿；ℹ️ 不影响退出码，但要逐条解释。
2. 哨兵版本 == `v<package.json 的 version>`；marker 的 `version` 同值，且没有意外的"本地已定制"跳过。
3. 逐模块确认：AGENTS 纪律段 / 契约 §9 / 总契约单表 / 能力契约 `capability-schema: 3`。
4. 出**验收报告**：基线输出 vs 现在（差异逐行说明）、已迁移项、**未完成项 + 卡在哪**、需用户决定的遗留项。

### 硬性禁止（越界即停下问）

1. **不自动迁移文档结构**：无逐批确认不许批量重写契约/总契约/计划；不许顺手"美化"没被要求的章节。
2. **不删任何文档**：归档只做"`合并状态=已合并` 且契约已承接 → `git mv` 进 `计划/归档/`"；是否清理由人决定。
3. **不擅自改依赖与 CI**：除第 2 步那一个依赖 tag，其他依赖/脚本/CI 不动。
4. **不动上游 tag 与版本**：不在框架仓库新建/移动/删除 tag，不改官方 `package.json` 版本。
5. **不整份覆盖模板**：项目档案与契约是**自有资产**，只"对齐"不"回灌"。
6. **拿不准的项列成待决清单交用户**。
