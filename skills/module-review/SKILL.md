# 模块审查技能（module-review）

自动定位：读档案（**应用清单路由** + 注入检查项）→ 读总契约（索引、应用拓扑）→ 读 `{文档根}/模块/{模块名}/` 核心文档（契约/接口）→ 对照**落点涉及的各应用代码**检查。

> **应用规范与分册的加载口径**：读应用规范的 §3.1 **主题索引**，按模块落点与「何时需要读」列**选读相关主题分册**——禁止全量加载所有分册（全部拼起来比原文件还大，分册就白拆了）；无关主题只读索引行。

> **触发**：显式触发词为 `/module-review {模块名}`（仅英文技能名触发）。

## 检查清单

### 一、通用清单（任何技术栈都查）

| # | 检查项 | 违规级别 |
|---|--------|---------|
| 1 | 契约↔代码文件一致性（契约声明的表/字段/状态机与代码、SQL 一致） | HIGH |
| 2 | 接口.md 与契约 §4 概览一致（接口清单与权限标识对齐） | HIGH |
| 3 | 导航区完整（核心文档互链、关联文档存在、标杆代码路径有效）；**未生成的文件标"（待生成）"不算断链**；**待实现模块在建档前（合并增量的 create 分支执行前）契约不存在 → 不报断链**，改为核对"计划已完成但未建档"（见 #32） | MEDIUM |
| 4 | **回写查账**（校验 /module-code 的回写义务已履行：**跑 `doc-framework check`，看「文档落后检查」有无未回写提示**——机器判据，不再靠 AI 判断有没有写登记行；接口.md 与代码一致、总契约索引已更新仍按原判据） | 漏写即 HIGH |
| 5 | 软删除 / 乐观锁实现（按档案通用约定 + 应用层覆盖声明） | HIGH |
| 6 | SQL 参数化（无 `${}` 拼接用户输入） | CRITICAL |
| 7 | 无硬编码密钥/密码/Token | CRITICAL |
| 8 | 输入校验（新增/修改接口参数有校验） | MEDIUM |
| 9 | 依赖注入存在性（注入的 Service/接口确实存在） | CRITICAL |
| 10 | **生产 SQL 登记完整**（变更含需人工在生产执行的 SQL 时，契约 §10 已登记且状态属实，SQL 文件存在于**所属服务**的 `sql/change/`） | 漏登即 HIGH |

### 二、多应用对账（应然 ↔ 实然）

| # | 检查项 | 违规级别 |
|---|--------|---------|
| 11 | **落点对账（契约 ⊆ 代码事实）**：契约 §5 落点表声明的每个应用，代码落点真实存在（契约有、代码无 = 漏实施）；代码有落点但契约未登记 = 可能私建（**在途计划豁免**见 #33） | HIGH |
| 12 | **计划表态对账**：近期已完成计划的「逐应用表态」属实——表态「本次不改」的应用代码零变更（用 `git diff --name-only` 核对，或提示用户跑 `doc-framework diff-check`）；实际改动 ⊆ 计划变更文件清单 | HIGH |
| 13 | **接入状态对账**：接口.md §5 各应用接入状态与各应用代码事实一致（标 ✅ 的端确实在调用，标 ❌ 的确实未接） | MEDIUM |
| 14 | **跨服务契约一致性**：聚合层/消费方调用的下游接口路径、字段、错误码与主责服务接口.md（服务端真相）一致 | HIGH |
| 15 | **跨应用不变量**：状态机（状态/流转/驳回语义）、权限标识、枚举 code 在各应用间完全一致——任何一端自定义即违规 | CRITICAL |
| 16 | **应用清单健康**：契约主责服务、§5 落点应用、接口.md 服务归属都在档案应用清单内；各应用代码根存在且无互相嵌套 | HIGH |

### 三、完成度对账（Completeness：计划任务 ↔ 实际产出）

> 审查维度说明：一、三节管 **Correctness**（实现是否符合契约），本节管 **Completeness**（计划声称做完的，是否真的做完）——两者都过才算可提交。

| # | 检查项 | 违规级别 |
|---|--------|---------|
| 17 | **任务勾选属实**：计划「任务清单」**勾选行**逐项核对——已勾选但无对应实现（假勾选）、有实现却未勾选（漏勾）都要列出并纠正。**登记行（人工步骤，无勾选框）不入勾选对账**（AI 不执行、也无框可勾）；但**勾选行里带了 `【人工·…】` 标记**即矛盾写法（AI 勾不了的活不该有勾选框），如实指出并回 `/module-plan` 去掉方括号 | HIGH |
| 18 | **状态与进度一致**：存在未勾选的**勾选行**却已登记「已完成」，或勾选行全勾但状态仍是「实施中」——两者都不一致。**登记行不参与此判据**（它只显示、不阻塞「已完成」） | HIGH |
| 19 | **验收场景可追溯**：计划 §7 验收项引用了契约 §8.2 的场景编号（SC-n），且场景在契约中确实存在；（若有测试文档）测试.md 用例标注了对应场景 | MEDIUM |
| 20 | **归档纪律**：状态为「已完成/已废弃」的计划是否已**归档**（`合并状态=已合并` → 文件移入 `计划/归档/`）；长期滞留活跃目录会让在途列表失真。**归档后是否清理由人决定，不判缺失** | LOW |

### 四、测试覆盖完整性（对照 测试规范 §1.1）

> 以下检查项仅在模块生成了测试文档（测试.md）时适用；未生成测试文档的模块跳过本节。

| # | 检查项 | 违规级别 |
|---|--------|---------|
| 21 | **黑盒底线**：测试.md 存在「适用层与依据」，且**接口层（黑盒）标注适用**并有用例 | 缺失即 HIGH |
| 22 | **白盒适用判定**：模块涉及持久化状态 / 流程实例反写 / 软删除 / 乐观锁之一时，库层（白盒）必须适用且有断言；不适用必须写原因（不可用"写起来麻烦"作理由） | 该做未做且无理由即 HIGH |
| 23 | **端层/编排层适用判定**：契约 §5 有前端应用落点 → 端层适用；涉及 ≥2 个服务端应用 → 编排层适用；不适用写明原因 | 该做未做即 MEDIUM |

### 五、处理方式与增量对账（对应 /module-doc 的 合并增量 / 代码对账 / 产物补齐）

| # | 检查项 | 违规级别 |
|---|--------|---------|
| 24 | **跨应用共享内容归位（双向）**：应用规范/契约里出现"≥2 个应用/模块必须一致遵守"的约定却未落 `边界/{能力}边界.md`（`check` 的"跨应用同题"判据可作线索）；**反过来**，边界文档已经拥有该约定、契约里仍保留同题材正文 → 判重复（应删正文、只留回链）；边界文档只剩一个消费者 → 应解散回写 | MEDIUM |
| 25 | **应用规范四不写**：应用规范出现变更痕迹（版本号/日期/`来源=`/修订沿革/取证过程）、代码清单（文件/方法/签名枚举，应回链代码路径）、缺口/待办登记（应归计划）→ 任一命中（`check` 规范层判据同款）。契约的历史/代码清单分别由 #35/#42 专管，避免重复判 | MEDIUM |
| 35 | **契约历史痕迹**：契约 §1–§8 出现日期+动词、版本号、`来源=`、修订沿革、`已作废/已退场`、`原文保留` → 历史应归 git；`check` 默认 note、`--strict` 升 warn | HIGH |
| 36 | **契约重复能力契约**：契约头部“委托给”的边界文档已拥有某条规则，§7/§5 仍保留同题材正文（不是一行回链）→ 应移动/删除，不是复制 | HIGH |
| 37 | **契约健康预算**：§7 >15KB 或 >20 条不变量 + 10 条陷阱、单条 >800B、§5 单元格 >2KB、§4.2 说明 >120 字、契约总量 >50KB → 先压缩/上移，再判是否可提交 | MEDIUM |
| 38 | **SC 完整性**：§8.2 索引表与 `#### Scenario:` 正文不是 1:1、ID 重复、ID 不是 `SC-{模块名}-{NN}`、引用的 SC 不存在、跨模块场景被复制 → 验收注册表不可信 | HIGH |
| 39 | **所有权声明**：契约头部缺“本契约拥有 / 委托给 / 本契约不拥有”三行；`委托给` 路径不存在；`本契约拥有` 为空 → 无法判断文档边界 | MEDIUM |
| 40 | **平台能力契约**：`平台-能力` 契约缺消费者表、失败模式（401/403/超时/降级/重试）、能力级验收；或把各端构建/目录/配置写成平台能力语义 | MEDIUM |
| 41 | **能力契约完整性**：`边界/{能力}边界.md` 缺主责/消费者表、缺 §5 失败模式、缺 §6 验收（有 ≥2 消费者时）、缺 §7 关联代码；只剩 1 个消费者却未解散 | MEDIUM |
| 42 | **契约含代码清单/构建步骤**：契约出现文件/方法/签名枚举、逐目录说明、构建命令、SDK 接入步骤 → 应回链应用规范/能力契约/代码路径 | MEDIUM |
| 26 | **增量合并完整性**：计划标 `合并状态=已合并`，但契约/接口.md 缺少该增量对应内容，或标记与契约事实不符（假合并）；计划「语义增量」的条目未被契约正文覆盖 | HIGH |
| 32 | **待实现模块已实施但未建档**：模块已有代码、契约缺失、且无在途计划（在途计划定义见下）→ 说明首次建模计划的 create 分支未执行 | HIGH |
| 33 | **无计划外漂移（私建）**：代码出现契约未登记的字段/表/接口/状态机状态/权限标识/落点。**在途计划豁免**：同模块存在在途计划（`状态 ∈ {已批准, 实施中, 已完成}` 且 `合并状态=待合并`）时，其「语义增量」覆盖的对象不计私建——否则实施 → 合并窗口内必然误报 | HIGH |
| 34 | **应用规范与其详细层事实源口径冲突**：应用规范声明的"冲突以谁为准"与其引用的详细层（应用仓库 AGENTS.md / 仓库内详细规范）口径相反，或两个应用对同一共享规则各执一词且无边界文档仲裁 | HIGH |

> **"在途计划"定义**（本技能统一口径，#26 / #32 / #33 共用）：同模块存在状态 ∈ {已批准, 实施中, 已完成} **且 `合并状态=待合并`** 的计划——已合并的增量已落账、无需豁免（判据见 #33）。
> **#26 / #32 / #33 的判定顺序**：先看有没有在途计划 → 有则核对增量覆盖范围（#26/#33 豁免）→ 无在途计划而代码已落、契约缺失（#32）。

### 六、档案注入清单（按应用读取）

按项目档案「技术栈特有检查项」**逐应用**执行（如 svc-main 的"继承统一 Controller 基类"、app-web 的"按钮权限指令控制"），只检查对应应用的代码。

### 七、通道合规审计（对应 /module-code 三通道，**事后审计**）

> 这是直改/轻量通道的安全网：免计划换来的低摩擦，靠这一节防"慢慢吃掉先文档后代码的纪律"。

| # | 检查项 | 违规级别 |
|---|--------|---------|
| 27 | **本该建计划却走了轻量/直改**：近期 git 变更触及契约语义（新增/改字段、表、接口、状态机状态、权限标识、跨应用不变量）或含 SQL，却没有对应的完整计划——即"用低档位承接了高档位改动" | HIGH |
| 28 | **直改边界越界**：无计划的改动落在契约 §5 落点之外的应用代码根（跑 `doc-framework diff-check --module {模块名}` 核对；文档回写不受限） | HIGH |
| 29 | **轻量计划形态合规**：轻量计划缺「逐应用表态」或「变更文件清单」（`check` 同款硬报错）；或本该完整（触语义/含 SQL/跨模块/需设计决策）却标了轻量 | HIGH |
| 30 | **作用域就地篡改**：已批准/已完成计划的「逐应用表态 / 变更文件清单 / 语义增量」被改动，但该改动**晚于本计划登记「已批准」的那次提交**（计划不记修订史 ⇒ 判据在 git：`git log --format='%h %ct %s' -- <计划路径>` 比对状态行的改动时点；扩作用域必须走「退回修订中 → 重新批准」，重新批准会再产生一次状态行改动）；「已完成」计划被追加任务项 | HIGH / MEDIUM |
| 31 | **直改 trailer 声明的真实性**：声明 `契约:无需变更` 的近期提交，其改动是否真的不触契约语义（抽样 AI 判——这是机器判不了的：#4 查"有没有未回写"，本条查"声明没说实话"；声明无需变更但实际改了字段/接口/状态机 = 直改通道被滥用） | MEDIUM |

判定方法：`git log --name-only` 取近期变更集合 → 按档案应用清单归属应用 → 对照契约 §5 落点与计划白名单 → 落到上表任一行。

## 输出格式

```
## {模块名} 代码审查报告

### CRITICAL（必须修复）
| # | 检查项 | 文件 | 问题描述 |

### HIGH（强烈建议修复）
| # | 检查项 | 文件 | 问题描述 |

### MEDIUM（建议修复）
| # | 检查项 | 文件 | 问题描述 |

### LOW（可选修复）
| # | 检查项 | 文件 | 问题描述 |

### 检查统计
- 总检查项: N / 通过: N / CRITICAL: N / HIGH: N / MEDIUM: N / LOW: N

### 完成度（Completeness，对应第三节）
- 计划: YYYY-MM-DD-{主题}.md（状态: {实施中/已完成}）
- 任务进度: x/y ｜ 未完成项: {编号 + 原因，或"无"}
- 人工步骤（登记行）: {编号 + 动作，或"无"}（无勾选框、不阻塞「已完成」；只确认它确实不由 AI 执行）
- 勾选异常: {假勾选 / 漏勾 / 勾选行带人工标记 / 无}

### 测试覆盖（Completeness，对应第四节）
- 接口层（黑盒）: {适用/缺失} ｜ 库层（白盒）: {适用且有断言 / 不适用+原因 / 该做未做} ｜ 端层: {…} ｜ 编排层: {…}

### 通道合规（对应第七节）
- 直改（无计划）: {无 / N 次} ｜ `diff-check --module`: {通过 / 越界 N 处} ｜ 提交信息 `契约:无需变更` 声明真实性: {属实 / N 处存疑}
- 轻量计划: {N 份} ｜ 形态合规: {是 / 否 + 原因}

### 增量与建档（对应第五节）
- 在途计划: {N 份（状态/合并状态）} ｜ 待合并增量: {N 项}
- 合并完整性: {通过 / 假合并 N 处} ｜ 文档落后检查（check）: {通过 / 未回写 N 处}
- 未建档的待实现模块: {无 / 模块名（计划路径）}
```

全部检查完成后，如果 CRITICAL 和 HIGH 均为 0，提示用户可提交；否则列出问题并建议相应修复：
- 文档/接口不一致 → `/module-doc {模块名}`（自动判定：代码是既成事实走代码对账；计划已完成但增量未落账走合并增量）；
- 代码问题 → `/module-code`（按计划修复）；
- 测试覆盖缺失 → 场景来源二选一：**代码已实现该行为（只是没登记）** → `/module-doc {模块名}` 代码对账补登 §8.2；**尚未实现** → 写进计划（已建档模块 → 「语义增量」；待实现模块 → 「建模补充」M2），实施后由 `/module-doc` 的「合并增量」落账；
- **通道用错**（本该建计划却直改/轻量）→ `/module-plan {模块名}`（补完整计划，语义写进「语义增量」节）→ `/module-code` → `/module-doc {模块名}`（合并增量）；若代码与契约已漂移，先 `/module-doc {模块名}` 代码对账；
- **直改越界**（改了落点外应用）→ 定性：漏登记落点则在计划的「语义增量」登记落点行（实施后由合并增量写进 §5）；越权改动则回滚并按计划通道重做。

**另外**：若计划存在未勾选的**勾选行**却已登记「已完成」，直接指出并要求按事实修正（回 `/module-plan` 修订状态，或 `/module-code` 补齐未完成项）——状态是事实登记，不允许"完成度不够但状态已完成"。**登记行（人工步骤）不在此列**（它无框可勾、不阻塞「已完成」；生产/平台侧步骤的完成时机由人定），但若**勾选行**里带了 `【人工·…】` 标记，要求回 `/module-plan` 去掉方括号改成登记行。
