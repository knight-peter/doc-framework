# 实施计划技能（module-plan）

负责实施计划的**创建 / 修订 / 状态流转**。与 /module-doc、/module-code 分工：**契约归 /module-doc、计划归 /module-plan、代码归 /module-code**，/module-review 兜底校验一致性。

> **触发**：显式触发词为 `/module-plan`（仅英文技能名触发）。

## 计划落盘位置

- **单模块计划**（默认）：`{文档根}/模块/{模块名}/计划/YYYY-MM-DD-{主题}.md` —— 路径含模块名，定位零歧义；
- **跨模块计划**（引用多个契约）：`{文档根}/计划/YYYY-MM-DD-{主题}.md` —— 全局目录专放跨模块主题；
- **归档位置**（已完成 / 已废弃的计划）：单模块 `模块/{模块名}/计划/archive/`、跨模块 `计划/archive/` —— **物理分离**，让"在途计划"列表永远干净（归档是独立动作，见 §2.3）。

文件名必须带日期前缀（便于归档）；一契约可对应多份计划，按 **日期+主题** 区分。

## 0. 定位目标计划 / 归档（按精度优先）

| 触发 | 定位方式 |
|------|----------|
| `/module-plan {计划路径}` | 路径直达（绝对或相对路径，相对以项目根为基准；归档计划只能这样读） |
| `/module-plan {模块名} {YYYY-MM-DD-主题}` | 日期+主题精确匹配 `模块/{模块名}/计划/` 下文件名 |
| `/module-plan {模块名}` | glob `模块/{模块名}/计划/*.md`（**不含 `archive/` 子目录**）列出清单供选择；无匹配则进入"新建" |
| `/module-plan {模块名} 归档` | 归档动作（见 §2.3），列出该模块可归档计划（状态=已完成/已废弃） |

只给模块名时，清单按 **编号 | 日期-主题 | 状态 | 修订版本 | 任务进度** 列出（例：`1. 2025-09-01 用户登录改造 [实施中] v2 3/8`），用户回复编号即定位。**归档计划不进清单**（保持活跃视图干净），需要时用路径直达。

## 1. 读上下文（创建时）

1. 读项目档案——**先读「应用清单」**（路由表：应用 → 类型/代码根/依赖），再读通用约定；
2. 读 `{文档根}/模块/{模块名}/` 四件套——契约 = 约束（§3 数据模型 / §4 接口概览 / **§5 应用落点表** / §8.2 验收场景）、接口.md 字段细节（含**消费方**列）；
3. 涉及跨模块/跨服务能力时读对应边界文档。

## 2. 创建 / 修订 / 归档

### 2.1 新建

按模板 `templates/计划/YYYY-MM-DD-{实施主题}.md.tpl` 渲染（状态=待审核，修订记录 v1），必备章节：需求理解 / **逐应用表态** / 变更文件清单（按应用分节）/ **任务清单（勾选式，可独立验证的最小步骤）** / **实施顺序（依赖序）** / 关键设计决策 / 接口兼容性声明 / 验收标准（引用契约 §8.2 场景编号）/ 待确认事项 / 里程碑 / **回写清单**。向用户汇报并等待确认。

**跨模块计划的契约前置护栏（硬性）**：创建跨模块计划（落盘 `{文档根}/计划/`）前，**校验计划将引用的每个模块契约都已存在**（逐个 stat `模块/{模块名}/契约.md`）。

- 契约缺失 → **不建计划**，提示：先逐模块 `/module-doc {模块名}` 产出契约（若来自探索，按"先逐模块契约 → 再跨模块计划"的顺序），再回来建计划；
- 理由：`/module-code` 执行跨模块计划时逐个读这些契约作为约束；空引用的计划 = 代码没有约束依据，直接违反"契约为约束"。

**影响面分析（逐应用表态的依据，禁止拍脑袋）**：

1. 从契约 §5 应用落点表取出本模块涉及的应用集合；
2. 按需求判断每个应用是否本次要动：字段/接口变了 → 看接口.md「消费方」列，消费该接口的应用都是候选；
3. 每个受影响应用显式标注 `改动 / 本次不改 / 不适用`——**漏表态 = 漏改**（红线）；表态「改动」的应用必须在变更文件清单中有对应文件（路径必须落在该应用代码根下）；
4. 实施顺序从应用拓扑推导：SQL（各服务 `sql/change/`）→ 主责服务（**接口契约先行**：接口.md 先定稿）→ 下游/聚合服务 → 逐端；
5. 涉及接口变更时填「接口兼容性声明」：破坏性变更（删/改字段、改路径、改语义）必须让所有消费方表态「改动」；
6. **任务清单**按实施顺序阶段（1.x SQL / 2.x 主责服务 / 3.x 下游聚合 / 4.x 逐端 / 5.x 测试回写）编写，粒度到"可独立验证的一个文件/接口/断言"；**不写无法验证的任务**（如"优化代码"）。

### 2.2 修订

1. 加载目标计划（按 §0 定位）；
2. 展示当前 **状态 + 待确认事项 + 修订记录**，用户给出修改意见；
3. 编辑正文 → **修订记录追加一行**（版本+1、日期、状态、修改点、评审结论）——追加式，不覆盖历史；
4. 状态流转（红线）：
   - 「已批准」→ 必须先退回「修订中」→ 修订 → 「待审核」重新评审（**不允许直接修改已批准计划**）；
   - 「待审核 / 修订中」→ 修订完 → 「待审核」；
   - 否决 / 放弃 → 「已废弃」（终态，注明原因）。

### 2.3 归档（独立动作，让在途列表保持干净）

触发：`/module-plan {模块名} 归档` 或 `/module-plan {计划路径} 归档`。

1. 列出候选（状态 = `已完成` / `已废弃`）；**未完成（待审核/修订中/已批准/实施中）的计划禁止归档**，提示先按状态机处理；
2. 移动文件到归档位置：单模块 `模块/{模块名}/计划/archive/`、跨模块 `计划/archive/`（`git mv` 保留历史）；
3. **不改状态、不改修订记录**——状态字段是事实登记，位置变化由路径体现，Git 历史可追溯；
4. 归档后该计划**不再进入任何 glob 清单/默认定位**（需路径直达才能读）；`/module-code` 不再接受其执行。

> 为什么归档是独立动作而不是 /module-code 自动移动：「实施完成」与「可以归档」是两件事——归档意味着该计划彻底退出活跃视图，由人来决定时机（可能还要等生产 SQL 执行、等验收）。这也让"在途计划"列表始终等于"真正在办的事"。

## 3. 状态约定

- 状态枚举：`待审核 / 修订中 / 已批准 / 实施中 / 已完成 / 已废弃`（**归档不是状态**，是位置：已完成/已废弃的计划可移入 `计划/archive/`）；
- 状态是**事实登记**：AI 登记、用户确认流转；评审可在文档内或文档外进行，状态如实记录即可，不强制流程；
- 实施类状态（实施中 / 已完成）由 /module-code 实施时登记，本技能不登记。

## 4. 边界

- 计划评审中发现契约缺口（如意向改动的应用未在契约 §5 落点表登记）→ 提示 `/module-doc {模块名}`（模式 A 需求驱动；**落点先登记后实施**），不得绕过契约直接改计划；
- 归档后的计划**不作规范依据**，长期看契约"变更记录"章节；
- **归档是 /module-plan 的职责**：/module-code 只登记「已完成」状态并提示归档，不移动计划文件；
- 本技能不实施代码、不回写契约变更记录（归 /module-code）。

## 与 /module-doc、/module-code 的协作约定

| 场景 | 流程 |
|------|------|
| 正向开发 | `/module-doc {模块名}`（模式 A 契约先行）→ `/module-plan`（创建计划）→ `/module-code {计划路径}`（实施+回写）→ `/module-doc {模块名}`（收尾） |
| 改造 | `/module-doc {模块名}`（模式 A 更新契约）→ `/module-plan`（新计划或修订）→ `/module-code`（实施+回写） |
| 计划未批准 | `/module-code` 拒绝执行 → 提示 `/module-plan` 处理（修订或废弃） |

/module-review 兜底校验文档与代码一致性（含多应用对账与回写查账）。
