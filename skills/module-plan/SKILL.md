# 实施计划技能（module-plan）

负责实施计划的**创建 / 修订 / 状态流转**。与 /module-doc、/module-code 分工：**契约归 /module-doc、计划归 /module-plan、代码归 /module-code**，/module-review 兜底校验一致性。

> **触发**：显式触发词为 `/module-plan`（仅英文技能名触发）。

## 计划落盘位置

- **单模块计划**（默认）：`{文档根}/模块/{模块名}/计划/YYYY-MM-DD-{主题}.md` —— 路径含模块名，定位零歧义；
- **跨模块计划**（引用多个契约）：`{文档根}/计划/YYYY-MM-DD-{主题}.md` —— 全局目录专放跨模块主题；
- **归档位置**（已完成 / 已废弃的计划）：单模块 `模块/{模块名}/计划/归档/`、跨模块 `计划/归档/` —— **物理分离**，让"在途计划"列表永远干净（归档是独立动作，见 §2.3）。**归档后的计划文件不自动删除**：什么时候清理由人决定（`git rm` 也在 git 历史里留痕）。

文件名必须带日期前缀（便于归档）；一契约可对应多份计划，按 **日期+主题** 区分。

## 0. 定位目标计划 / 归档（按精度优先）

| 触发 | 定位方式 |
|------|----------|
| `/module-plan {计划路径}` | 路径直达（绝对或相对路径，相对以项目根为基准；归档计划只能这样读） |
| `/module-plan {模块名} {YYYY-MM-DD-主题}` | 日期+主题精确匹配 `模块/{模块名}/计划/` 下文件名 |
| `/module-plan {模块名}` | glob `模块/{模块名}/计划/*.md`（**不含 `归档/` 子目录**）列出清单供选择；无匹配则进入"新建" |
| `/module-plan {模块名} 归档` | 归档动作（见 §2.3），列出该模块可归档计划（状态=已完成/已废弃） |

只给模块名时，清单按 **编号 | 日期-主题 | 状态 | 修订版本 | 任务进度** 列出（例：`1. 2025-09-01 用户登录改造 [实施中] v2 3/8`），用户回复编号即定位。**归档计划不进清单**（保持活跃视图干净），需要时用路径直达。

## 1. 读上下文（创建时）

1. 读项目档案——**先读「应用清单」**（路由表：应用 → 类型/代码根/依赖），再读通用约定；
2. **存量模块**（有契约）：读 `{文档根}/模块/{模块名}/` 四件套——契约 = **已生效语义 + 长效不变量**（§3 数据模型 / §4 接口概览 / **§5 应用落点表** / §8.2 验收场景）、接口.md 字段细节（含**消费方**列）；语义变更**不写进契约**，写进本计划的「语义增量」节；
3. **待实现模块**（代码库零实现、无契约）：读 `/module-explore` 的探索记录（`{文档根}/探索/YYYY-MM-DD-{主题}.md`，含「待实现模块清单与关系」节）+ 总契约依赖矩阵；没有探索记录 → 按 §2.1 的编号门处理（先补探索，或人工降级写 `无（自述）`）；
4. 涉及跨模块/跨服务能力时读对应边界文档。

## 2. 创建 / 修订 / 归档

### 2.0 计划形态（完整 / 轻量，按判据选，不按"感觉"选）

计划格式只有一种，**两个档位**；形态由改动性质决定（与 /module-code §0.1 三通道判据一致）：

| 形态 | 何时用 | 必备章节 | 可标"无/不适用"的章节 |
|------|--------|----------|------------------------|
| **完整**（默认） | 触及契约语义、含 SQL、跨模块、需留设计决策 | 需求理解 / 逐应用表态 / **语义增量** / 建模补充（仅首次建模） / 变更文件清单 / 任务清单 / 实施顺序 / 关键设计决策 / 接口兼容性声明 / 验收标准 / 回写清单 | 待确认事项、里程碑；语义增量为空时写"无（纯实现改动）"并把 `合并状态` 标 `无需合并` |
| **轻量** | **不触契约语义、无 SQL、无需设计决策**，且**跨应用或改动面大**（单应用 + 预计 ≤5 文件 + 无决策 → 走 `/module-code` 直改通道，不必建计划） | **逐应用表态 / 变更文件清单 / 任务清单**（三节缺一不可——表态+清单是白名单，任务清单是进度） | 需求理解、**语义增量（整节删除）**、实施顺序、关键设计决策、接口兼容性、验收标准、回写清单 |

- 渲染后必须显式写头部一行 `> 计划形态：完整` 或 `> 计划形态：轻量`（`check` 据此校验：**轻量计划缺表态或缺清单 → 硬报错**；**轻量计划不得含语义增量节**——轻量不承载语义，发现触语义必须升级完整计划）；
- **完整形态的「语义增量」节位置固定**：在「逐应用表态」之后、「变更文件清单」之前（先语义后文件）；含 `> 合并状态：待合并 | 已合并 | 无需合并` 一行；
- **首次建模计划**（待实现模块）额外要求：必须**完整形态** + 「语义增量」写全量目标语义 + **「建模补充」节（M1 边界 / M2 状态机与页面结构 / M3 依赖与集成点 / M4 验收 Scenario）**——缺任一项 `check` 硬报错；
- 轻量计划**不是免批准**：仍走 `待审核 → 已批准`，红线一样；
- 判据说"该建完整计划却建了轻量的" → /module-review 判 HIGH（见该技能"本该建计划却走轻量/直改"检查项）。

### 2.1 新建

按模板 `templates/计划/YYYY-MM-DD-{实施主题}.md.tpl` 渲染（状态=待审核，修订记录 v1，**标明计划形态**）。

**依据填写（二选一，决定计划类型）**：

| 模块状态 | 头部字段 | 说明 |
|----------|----------|------|
| 存量（有契约） | `> 依据模块契约：\`{契约路径}\`` | **必须指向已存在的契约**（`check` 新增硬校验）；无契约引用 → 硬报错 |
| 待实现（零实现、无契约） | 删除 `依据模块契约` 行，填 `> 依据探索记录：\`{探索记录路径}\`` | 判定式＝**无 `依据模块契约` ∧ 有 `依据探索记录`** ⇒ 首次建模计划；路径必须存在 |

- 待实现模块**没有探索记录**时，只问一次（编号门，禁止 AI 自降级）：`1) 先跑 /module-explore（推荐）2) 就地建计划并标注 依据探索记录=无（自述）`——选 2 时 `check` 给 ℹ️（哨兵值只允许由用户选择后写入，AI 不得自行省略该字段）；
- **跨模块计划**若依赖尚未建档的待实现模块，`依据模块契约` 可指向该模块的**首次建模计划路径**（取值域已放宽）。

**存量 ↔ 待实现 的判定要用证据，不靠感觉**：`契约.md` 已存在 ⇒ 存量；`变更文件清单` 里的文件**全部已存在** ⇒ 疑似存量（`check` 在未进入实施时硬报错）。

> **命名固定中文**（v2.6.0 起不再支持英文产物命名）：计划落盘 `{文档根}/模块/{模块名}/计划/YYYY-MM-DD-{主题}.md`（跨模块 `{文档根}/计划/`），头部字段用 `> 状态：` / `> 计划形态：` / `> 依据模块契约：` / `> 依据探索记录：` / `> 合并状态：`，章节用 `逐应用表态` / `变更文件清单` / `任务清单` / `回写清单` / `接口兼容性声明` / `语义增量`（ADDED/MODIFIED/REMOVED 三表 + `主计划` 列）/ `建模补充`，状态用中文枚举——解析器按这些关键词定位，命名必须一致（完整清单见框架仓库 `docs/设计文档.md` §8.1）。

**完整形态**必备章节：需求理解 / **逐应用表态** / **「语义增量」**（语义变更的唯一载体；纯实现改动写"无（纯实现改动）"并标 `合并状态：无需合并`） / 变更文件清单（按应用分节）/ **任务清单（勾选式，可独立验证的最小步骤）** / **实施顺序（依赖序）** / 关键设计决策 / 接口兼容性声明 / 验收标准（引用契约 §8.2 场景编号）/ **回写清单**；**待确认事项 / 里程碑**按需填写（无则写"无"）。首次建模计划另需「建模补充」节（M1–M4）。向用户汇报并等待确认。

**轻量形态**只渲染三节（逐应用表态 / 变更文件清单 / 任务清单）+ 头部状态与形态；其余节删除而非留空模板（空节会让 review 与 check 误判）。

**跨模块计划的契约前置护栏（硬性）**：创建跨模块计划（落盘 `{文档根}/计划/`）前，**校验计划将引用的每个模块依据都已存在**——逐个 stat `模块/{模块名}/契约.md`，**或**该模块的首次建模计划文件（未建档的待实现模块）。

- 两者都不存在 → **不建计划**，提示：存量模块先 `/module-doc {模块名}` 代码对账产出契约；待实现模块先 `/module-plan {模块名}` 建首次建模计划（若来自探索，按"先逐模块计划/契约 → 再跨模块计划"的顺序）；
- 理由：`/module-code` 执行跨模块计划时逐个读这些依据作为约束；空引用的计划 = 代码没有约束依据。

**影响面分析（逐应用表态的依据，禁止拍脑袋）**：

1. 从契约 §5 应用落点表取出本模块涉及的应用集合（待实现模块从探索记录的「待实现模块清单与关系」+ 建模补充 M3 集成点取）；
2. 按需求判断每个应用是否本次要动：字段/接口变了 → 看接口.md「消费方」列，消费该接口的应用都是候选；
3. 每个受影响应用显式标注 `改动 / 本次不改 / 不适用`——**漏表态 = 漏改**（红线）；表态「改动」的应用必须在变更文件清单中有对应文件（路径必须落在该应用代码根下）；
4. 实施顺序从应用拓扑推导：SQL（各服务 `sql/change/`）→ 主责服务（**接口语义已在「语义增量」节定稿**，实施时按其落地）→ 下游/聚合服务 → 逐端；
5. 涉及接口变更时填「接口兼容性声明」：破坏性变更（删/改字段、改路径、改语义）必须让所有消费方表态「改动」；
6. **任务清单**按实施顺序阶段（1.x SQL / 2.x 主责服务 / 3.x 下游聚合 / 4.x 逐端 / 5.x 测试回写）编写，粒度到"可独立验证的一个文件/接口/断言"；**不写无法验证的任务**（如"优化代码"）。轻量形态按 1.x / 2.x… 顺序即可，不必套四层。

### 2.2 修订

1. 加载目标计划（按 §0 定位）；
2. 展示当前 **状态 + 形态 + 待确认事项 + 修订记录**，用户给出修改意见；
3. 编辑正文 → **修订记录追加一行**（版本+1、日期、状态、修改点、评审结论）——追加式，不覆盖历史；
4. 状态流转（红线，按修改内容分两类）：
   - **改作用域**（逐应用表态 / 变更文件清单 / 计划形态）= 改授权范围：「已批准」→ **必须先退回「修订中」** → 修订 → 「待审核」重新评审（**不允许直接修改已批准计划的作用域**）；
   - **改「语义增量」= 改授权语义**：同样**必须先退回「修订中」**重新批准（它是 /module-code 的目标与 /module-doc 合并的来源；已批准后只能追加"实施偏离"说明，不能就地改目标语义）；
   - **不改作用域**（在既定范围内追加任务项、勾选进度、补写说明）= 记账：**允许就地更新**，不必退回修订中（/module-code 执行期间也照此办理）；但「已完成」状态不得追加任务——那是新改动，新建计划或先退回修订中。
   - 「待审核 / 修订中」→ 修订完 → 「待审核」；
   - 否决 / 放弃 → 「已废弃」（终态，注明原因；**同时把 `合并状态` 写 `无需合并`**，否则该计划会永远挂在"待合并"）。
5. **I3：一份语义变更只由一份计划承载增量**——同模块下若已有另一份含非空增量、且「主计划」列为空的有效计划，则本计划必须在增量三表的「主计划」列回指它（`check` 对"两份都为空"硬报错）；拆分实施允许，但增量只能有一份主载体。

### 2.3 归档（独立动作，让在途列表保持干净）

> **模型**：计划是**单次决策记录**——它的价值在「审核期」（授权作用域 + 承载语义增量）与「归档后作为决策档案」（修订记录里有评审结论与批准口径）。所以归档 = **校验契约已完整登记 + 把提交 SHA 写进 §9 该行 + 移入 `计划/归档/`**。
> **归档 ≠ 删除**：**本技能不删除任何计划文件**。归档后的计划由**人**按需手动清理（`git rm`）；清了也不影响追溯——契约 §9 的回链凭据（提交 SHA）不依赖计划文件存活。**自动删除会让人丢失决策档案，且不可逆，所以不做。**

触发：`/module-plan {模块名} 归档` 或 `/module-plan {计划路径} 归档`。

1. 列出候选（状态 = `已完成` / `已废弃`）；**未完成（待审核/修订中/已批准/实施中）的计划禁止归档**，提示先按状态机处理；
2. **合并状态守卫（硬性）**：`状态=已完成 ∧ 合并状态=待合并`（含非空增量）→ **拒绝归档**，提示先跑 `/module-doc {模块名}` 把增量落账（翻 `已合并`）。`已废弃` 的计划允许归档，但归档前把 `合并状态` 写 `无需合并`（废弃是增量的第二条出口）；
3. **登记完整性守卫（硬性）**——归档前逐项确认契约已承接，**任一缺失则拒绝归档**：

   | 确认项 | 去哪看 |
   |---|---|
   | 语义增量三表每条已落账（正文 + `接口.md`） | 契约正文 / `接口.md`；计划 `合并状态=已合并` |
   | 本计划涉及的落点变化已进契约 §5 | 契约 §5 应用落点表 |
   | 验收场景已进契约 §8.2 | 契约 §8.2 |
   | 含生产 SQL 时已在契约 §10 登记 | 契约 §10 |
   | 计划「回写清单」逐项已勾 | 计划 §11 |
   | **契约 §9 有本计划对应的登记行** | 契约 §9（`来源=合并` 行；待实现模块另有 `create` 建档行） |

4. **把提交 SHA 记进契约 §9 登记行的回链**（`2026-09-08 财务模块金额统一成元 @a1b2c3d`）——这是**唯一不会消失的追溯凭据**：契约行 → 提交 → 当时真实的代码快照。即使日后计划文件被人清理，追溯链依然完整；
5. **移动文件到归档位置**：单模块 `模块/{模块名}/计划/归档/`、跨模块 `计划/归档/`（`git mv` 保留历史）；
6. **不改状态、不改修订记录**——状态字段是事实登记，位置变化由路径体现，Git 历史可追溯；
7. 归档后该计划**不再进入任何 glob 清单/默认定位**（需路径直达才能读）；`/module-code` 不再接受其执行。

> **为什么归档是独立动作而不是 /module-code 自动移动**：「实施完成」与「可以归档」是两件事——归档意味着该计划彻底退出活跃视图，由人来决定时机（可能还要等生产 SQL 执行、等验收）。这也让"在途计划"列表始终等于"真正在办的事"。
> **归档计划的清理**：由人决定是否 `git rm`（项目里堆积太多时）。**skill 不代劳**——删除是不可逆动作，而计划里的修订记录（评审结论、批准口径、被否方案）是决策档案；真需要清理时，先确认 §9 的凭据已写好。

## 3. 状态约定

- 状态枚举：`待审核 / 修订中 / 已批准 / 实施中 / 已完成 / 已废弃`（**归档不是状态**，是位置：已完成/已废弃的计划可移入 `计划/归档/`）；
- **形态枚举**：`完整 / 轻量`（头部 `> 计划形态：…`；只影响必备章节与校验强度，不影响状态机与红线）；
- **合并状态枚举**（头部「语义增量」节内 `> 合并状态：…`，三值）：`待合并`（增量已实施待落账）/ `已合并`（合并增量已落账）/ `无需合并`（空增量＝纯实现改动，或计划已废弃）。**只有 /module-doc 的合并增量处理完成后才翻 `已合并`**，/module-code 与 /module-plan 不得擅自翻；
- 状态是**事实登记**：AI 登记、用户确认流转；评审可在文档内或文档外进行，状态如实记录即可，不强制流程；
- 实施类状态（实施中 / 已完成）由 /module-code 实施时登记，本技能不登记；
- **批量归档入口**：`doc-framework list --stale {N}` 列出日期早于 N 天前的在途计划（归档候选），据此一次性归档一个迭代里攒下的小改单，而不是每改一次就归档一次。

## 4. 边界

- 计划评审中发现意向改动的应用未在契约 §5 落点表登记 → 在计划的「语义增量」ADDED 中登记该落点行（实施后由 `/module-doc` 合并进 §5），**不得绕过计划直接改契约正文**；
- **形态判定不得为了省事而降级**：触语义/含 SQL/跨模块一律完整形态；拿不准就问用户（编号确认），不自行降级；
- **长期真相是契约**：归档后计划不作规范依据，回看历史一律读契约「变更记录」（§9）——那里有日期、来源、结论与**提交 SHA**；计划本身作为决策档案保留，但**是否清理由人决定**；
- **归档是 /module-plan 的职责，删除不是谁的责任**：/module-code 只登记「已完成」状态并提示归档，不移动也不删除计划文件；本技能**不删除任何计划文件**；
- **"代码在前"的情形**：提交里没有计划作者，SHA 仍填该提交（追溯链的落点是"当时真实的代码"），并确认契约 §9 已按实际来源登记（`代码` / `实现`）；
- 本技能不实施代码；契约 §9 / §10 的**事实登记**按通道分工——直改通道由 `/module-code` 写 `来源=实现`，代码对账由 `/module-doc` 写 `来源=代码`，计划通道由 `/module-doc` 合并时写 `来源=合并`。

## 与 /module-doc、/module-code 的协作约定

| 场景 | 流程 |
|------|------|
| 正向开发（大改，存量模块） | `/module-plan {模块名}`（完整计划 + 「语义增量」= 语义设计与授权）→ 用户批准 → `/module-code {计划路径}`（实施 + 事实登记）→ `/module-doc {模块名}`（**合并增量** → 翻 `已合并`）→ `/module-review` → **归档**（契约 §9 记 SHA → 移入 `计划/归档/`；删除由人手动决定） |
| **待实现模块（首次建模）** | `/module-explore`（强制落盘探索记录）→ `/module-plan {模块名}`（首次建模计划：判定式见 §2.1 + 完整形态 + 建模补充）→ 批准 → `/module-code` 实施 → `/module-doc {模块名}`（**合并增量的 create 分支建档** + 回写总契约）→ `/module-review` |
| 改造 | `/module-plan`（新计划或修订；语义写进新计划的增量节）→ 批准 → `/module-code`（实施+回写）→ `/module-doc`（合并增量） |
| **小改（跨应用、不触语义）** | `/module-plan {模块名}`（**轻量计划**，三节，无增量节）→ 用户批准 → `/module-code {计划路径}`；作用域不变时后续小改**追加任务项即可** |
| 计划未批准 | `/module-code` 拒绝执行 → 提示 `/module-plan` 处理（修订或废弃） |
| 小到不值得建计划 | 建议走 `/module-code {模块名}` 的**直改通道**（边界=契约 §5 落点，一次编号确认） |

/module-review 兜底校验文档与代码一致性（含多应用对账与回写查账）。
