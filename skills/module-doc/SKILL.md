# 模块文档技能（module-doc）

负责模块核心文档（契约 / 接口）的**创建与更新**。分工：**文档归 /module-doc、代码归 /module-code**，/module-review 兜底一致性；**探索与讨论归 /module-explore**；**语义变更归 /module-plan**（写进计划的「语义增量」节）。

> **触发**：`/module-doc {模块名}`。**零后缀、零参数**——处理方式由 AI 探测后带编号请你确认；强制指定回编号或用自然语言。

## 0. 上下文自动发现（零路径投喂 + 应用路由）

1. 读项目档案——**先读「应用清单」（路由表）**：应用 → 类型/代码根/规范文件/数据库/依赖；再读文档根、语言、通用约定、标杆映射、文档导航；
2. 读总契约——§4 模块索引表（索引列 + 依赖列）、§5 依赖全景图、§3 应用拓扑；
3. **应用路由**：确定本模块涉及的应用（已有模块读契约 §5 落点表；待实现模块读计划的「建模补充」M1 集成点，推断不出**只问一次**主责服务与涉及端）；
4. 涉及跨模块/跨服务能力时读对应边界文档（缺索引则扫 `{文档根}/边界/`）；
5. 发现档案缺登记时**提示回填档案**，而非反问用户要路径。

## 1. 三种处理方式（按"真相来源"分）

| 处理方式 | 真相来源 | 产出（细化步骤见括注） |
|------|----------|--------------|
| **合并增量** | 已批准的计划「语义增量」 | 增量落账进契约正文 + 接口.md（**update 存量落账 / create 首次建档**，见 §2） |
| **代码对账** | 代码 | 分组差异清单 → 分组确认 → 回写契约 + 接口（见 §3；**待实现模块拒绝执行**） |
| **产物补齐** | 契约 | 前置检查通过后产出 **接口.md**（见 §4；测试文档与脚本归 `/module-test`） |

- **契约不承载未生效语义**：需求变更不再由本技能写进契约正文，而是 `/module-plan` 写进计划的「语义增量」节；实施后由**合并增量**落账；
- **处理方式共三种**：合并增量 / 代码对账 / 产物补齐（判定见 §1.1；待实现模块改走 `/module-plan` 的首次建模计划，不预建契约）；
- **命名纪律（对用户一律中文）**：探测事实、编号确认、完成汇报里只用**中文处理方式名**（`合并增量` / `代码对账` / `产物补齐`）；**禁止字母代号**（`M` / `B` / `C` / `A`）——对用户无语义（看不懂等于没说）。

### 1.1 判定：意图优先，状态校验（不可跳）

```
第 1 步：读用户意图（从话里取，不从状态猜）
   需求词（§1.4 词表）        → 语义变更，候选「/module-plan 增量」（见第 2 步）
   代码既成语（§1.4 词表）    → 候选 代码对账
   补产物词（§1.4 词表）      → 候选 产物补齐
   合并/落账词（"计划完成了""落账""合并增量"）→ 候选 合并增量
   无意图词                  → 进入第 2 步由状态推断

第 2 步：用仓库状态校验候选
   计划已完成 + 合并状态=待合并            → 合并增量（最高频入口）
   无契约 + 无代码（待实现模块）           → 【不归本技能】重定向 /module-plan（首次建模计划）
   无契约 + 有代码 + 需求词                → 【代码对账 → 合并增量 复合流程】（§5）：先代码对账建基线，需求写进计划增量，实施后合并增量
   无契约 + 有代码（无需求词）             → 代码对账（从零生成 契约+接口）
   有契约 + 需求词                        → 【语义变更不归本技能】重定向 /module-plan（增量）；实施完成后再回来走合并增量
   有契约 + 代码词                        → 代码对账（分组差异回写）
   契约与代码一致 + 产物缺失               → 产物补齐（前置检查见 §4）
   判定"不影响契约语义"                    → 【无需文档变更】结论（说明理由；若代码已改，提交信息写 `契约:无需变更`，见 §6 第 6 条）

第 3 步：冲突/低置信 → 只问一个问题二选一；仍不成形 → 重定向 /module-explore
```

**三条反直觉规则**（必须执行）：

1. 用户显式意图 > 状态推断；**不得因为"代码恰好存在"就自动走代码对账**；
2. 「代码对账」的触发条件是"用户确认代码是既成事实、不打算改代码"，不是"能读到代码"；
3. **无契约 + 有代码 + 需求词 = 复合流程**（先代码对账建基线，再走计划增量，实施后合并增量），不是二选一。

### 1.2 确认门（任何处理方式首写前一律确认；编号 = 强制入口）

**固定格式**（事实 + 处理方式 + 产物 + 编号备选）：

```
探测事实：计划 2025-01-02-订单改造 状态=已完成、合并状态=待合并（增量 3 项）→ 候选「合并增量」（存量落账）
将写入：契约 §3/§4/§5/§8 + 接口.md（留痕在 git 提交信息 trailer，不写契约 §9）
1) 确认按「合并增量」执行    2) 改为「代码对账」（以代码为准回写）    3) 改为「产物补齐」（只补 接口.md）
```

- 回复**数字** = 精确切换处理方式并视为确认（封闭输入，不依赖语义解析）；
- 回复自然语言同样生效；**用户显式指定时 AI 必须遵从**（即使与探测冲突），并记一句"**用户强制指定，覆盖探测**"；
- 执行中命中 §3.2 停条件才再次打断；否则一次确认走完；
- **不得擅自翻 `合并状态`**：只有**合并增量**完成合并后才翻 `已合并`。

### 1.3 探测规则表

| 探测事实 | 处理方式 |
|----------|------|
| 计划状态=已完成、`合并状态=待合并` | **合并增量**（update；待实现模块则 create） |
| **无契约 + 无代码**（待实现模块） | **重定向 `/module-plan`**（首次建模计划；建档链路见 §2.4 的 create 分支） |
| **无契约 + 有代码 + 需求词** | **代码对账 → 合并增量 复合**（§5） |
| 无契约 + 有代码（无需求词） | 代码对账 |
| 有契约 + 代码不一致（用户说"代码改了/同步"） | 代码对账 |
| 有契约 + 用户描述的是需求变更 | **重定向 `/module-plan`**（语义变更写进计划的增量节） |
| 契约与代码一致，但 接口.md 缺失或不完整 | 产物补齐 |
| 有契约 + 用户明确说"补齐接口" | 产物补齐 |
| 任一处理方式判定"不影响契约语义"（纯实现/文案/样式） | **无需文档变更**（说明理由后结束）；真要把代码改掉 → 走 `/module-code {模块名}` **直改通道**（免计划，边界=契约 §5 落点） |
| 用户给的是**主题**而非模块名，且需求不成形 | 不猜 → 提示 `/module-explore {主题}` |

### 1.4 词表（冲突判定的可复现依据）

- **需求词**：新增 / 增加 / 改成 / 要支持 / 应该 / 需要（描述期望行为）
- **代码既成语**：代码已经改了 / 线上就是这样 / 现在已经是 / 同步一下（把代码当事实）
- **补产物词**：出接口 / 补接口 / 出方案
- **合并词**：落账 / 合并增量 / 计划完成了 / 建档（待实现模块）
- **冲突信号**：同时出现需求词与代码既成语；或状态与意图矛盾；或代码落点含 TODO/空实现标记 → 走"只问一个问题"档。

### 1.5 旧后缀兼容（不宣传，但识别）

`新建`→ 重定向 `/module-plan`（首次建模计划）｜`补文档`→代码对账（无契约）｜`同步`→代码对账（有契约，**以代码为准**）｜`改造`→ 重定向 `/module-plan`（语义变更走计划增量）。旧后缀只作为自然语言提示被识别，不再是正式语法。

## 2. 合并增量（计划 → 契约，两分支）

> **前提**：计划状态=已完成（或有明确授权），且其「语义增量」已实施落地。合并**不是抄计划**——见 §2.3 铁律。

### 2.1 update 分支（契约已存在）

0. （推荐）先跑只读清单：`doc-framework check --draft-contract {计划路径}` —— 它按「目标位置」与「归属」把每条增量映射到目标文档，**保证不漏条目**（不写文件）；
1. 读计划「语义增量」（ADDED / MODIFIED / REMOVED 三表 + `主计划`/`归属` 列）与 §1「需求与思路」（§7 不变量/陷阱的来源）；
2. **先分类、再落笔**：逐条判归属——`能力契约` / `模块契约` / `接口` / `应用规范` / `总契约索引`；历史/决策不接收增量（→ git / 探索）；
3. 按「目标位置」逐条定位：能力契约 → `边界/{能力}边界.md`；模块契约 → §3/§4/§5/§7/§8；接口 → `接口.md`；应用规范 → `规范/应用-*.md`；总契约 → §4/§5/§7；
4. **以代码校正**（§2.3）：字段名/类型、路由、权限标识、落点路径一律从代码取；
5. **移动而非复制（§8）**：跨应用能力写/更新能力契约后，**删除模块契约里的副本**，只留一行回链；模块契约只保留“本模块必须遵守什么 + 违反时看到什么”；
6. **重写 + 压缩**：受影响章节按当前真相重写，删除被取代表述；禁止 append-only、禁止“旧条目保留原文”；§7 只保留本模块 `INV/TRAP`；
7. 写入契约 + 接口.md；接口.md §5 各应用接入状态按各端实际更新；新建/更新能力契约时回写 `总契约 §7 能力契约索引`；
8. **自检**：`doc-framework check` + `doc-framework audit --module {模块名}`；无历史痕迹、无 SC 失配、无“委托主题仍在 §7”；
9. 把计划的 `合并状态` 翻成 `已合并`；
10. 回写总契约（§4 模块索引表：索引列 + 依赖列；依赖有变时重绘 §5 全景图；能力契约变更加 §7；拓扑有变时同步 §3）。

> **留痕已改道 git**：契约 §9 不再有表、**不再追加任何行**；追溯凭据在代码提交信息里（trailer：`模块:`/`计划:`/`契约:`——格式权威见 AGENTS.md §5，此处不复述）。有偏离时在**提交信息**补「实施偏离：计划 X → 实际 Y」。

### 2.2 create 分支（待实现模块首次建档）

> **建档九步**（首次建模计划实施完成后执行）：

```
① 探测 + 编号确认门（1 现在建档 / 2 稍后）；可先跑 `doc-framework check --draft-contract {计划路径}` 取建档清单
② 读入五类输入：计划的「语义增量」/「建模补充」/ 代码实际 / 契约·接口模板 / 总契约+应用清单+探索记录
③ 渲染契约骨架（按模板全章；`模块形态=平台-能力` 用 `契约-平台能力.md.tpl`，其余用 `契约.md.tpl`）
④ 按 §2.4 映射表填 §2/§3/§4/§5/§8（目标语义来自增量 + 建模补充）；**§3.2 状态机图与 §5 页面结构图取自计划 §1.3**（按图前粗体标注分拣）
⑤ 以代码校正 §3/§4/§5（字段/路由/权限/落点）→ 不一致在提交信息备注「实施偏离：计划 X → 实际 Y」
⑥ 填头部导航区（业务域 / 形态 / 主责服务 / 建档方式 / 关联文档 / 标杆 / 核心文档回链）
⑦ 归属判定（§8）：增量中"≥2 个应用/模块必须一致遵守"的约定 → 写/建 边界/{能力}边界.md；**移动而非复制**，删除契约副本
⑧ 生成 接口.md（§1–§4 取自代码，§5 接入状态按各端实际）
⑨ 填所有权声明（拥有/委托/不拥有）、INV/TRAP、SC-{模块名}-{NN}；跑 `audit --module` 压缩
⑩ 回写总契约（§4 模块索引表 / §5 全景图 / §7 能力契约索引 / §3 应用拓扑）→ 翻 `合并状态=已合并` → 自检 `check` + `/module-review` 检查 11
```

### 2.3 铁律（两分支共用）：以代码为准，不照抄计划

- **计划是设计意图，契约是已生效事实**：字段名/类型、路由路径/方法、权限标识、各端文件路径**一律从代码取**；
- 计划与实际不一致 → 契约写**代码值**，偏离在**提交信息**备注「实施偏离：计划 X → 实际 Y」（不写进契约）；
- 合并后立即自检 `check` + `/module-review` 检查 11（契约 ⊆ 代码事实）——**合并动作自带验收**；
- **合并不是 append**：重写目标章节、删除被取代表述、把长文压成“当前真相 + 回链”；“旧条目保留原文/沿革”一律禁止（历史归 git）。合并完成前跑 `doc-framework audit --module {模块名}`，把 §7/§5/§8 的超预算项处理掉；
- 增量落账后计划**归档**（需 `合并状态=已合并`，否则 `/module-plan` 拒绝归档；归档流程唯一权威见 /module-plan §2.3）——归档的追溯链在 git：代码提交信息带 `计划:{计划标识}`（trailer 格式权威见 AGENTS.md §5）；

### 2.4 映射表（增量 + 建模补充 + 代码 → 契约章节）

| 契约章节 | 来源 |
|----------|------|
| 头部导航区 | 计划头部（模块名 / 主责服务 / 涉及应用）+ 应用清单（类型层规范）+ 同型标杆 + 核心文档回链 |
| §1 模块定位 | 计划 §1.1「需求」+ §1.2「实施后结果」+ §1.4「不做什么」（管什么/不管什么）+ 探索记录的"目标一句话"；平台能力必须填消费者表 |
| §2 边界约定 | §2.2「不做什么」取计划 §1.4（管什么/不管什么）+ 探索记录 §5 职责边界；§2.1 依赖以**代码实际调用**为准，计划「建模补充」M1 只作补充 |
| §3 数据模型 | 增量 ADDED 中 `契约 §3.x` 的行 + **代码实际 schema**；**状态机图取计划 §1.3** 中标 `**状态机**` 的 mermaid 块（以代码校正；存量计划改了状态机时同步替换本图） |

| 接口.md §1–§4 | **代码实际**（请求 / 响应 / 错误码 / 分页） |

| 总契约 §4 / §5 / §7 / §3 | 模块索引表行（索引列 + 依赖列）/ 全景图节点 / 能力契约索引（能力、主责、消费者）/ 应用拓扑（仅当引入新应用） |

## 3. 代码对账（以代码为准回写文档）

> 护栏：**不允许直接覆盖**——先出分组差异清单、分组确认、登记来源。**待实现模块拒绝执行**（没有代码可对，硬停并提示先 `/module-plan`）。

### 3.1 步骤

1. 按应用清单**逐应用**到其代码根 glob 定位落点代码（`*Controller.java`、`views/*/{模块}/`、`pages/{模块}/`、`pages.json` 等；路径从清单派生，禁止写死目录名）；
2. 读各应用落点代码（Controller / Service / Mapper / 各端页面）；
3. 产出**分组差异清单**：

   | 组 | 内容 | 默认 |
   |----|------|------|
   | **必改** | 接口路径/方法、状态机与枚举 code、权限标识、应用落点 | 建议全接受 |
   | **建议** | 字段名称/类型、必填性、错误码文案 | 逐组确认 |
   | **仅登记** | 字段说明、枚举文案、注释级差异 | 默认只登记不改契约 |

   行格式：`| # | 对账项 | 组 | 契约现值 | 代码事实 | 建议动作 | 置信度 |`

4. **分组确认**（可"只接受必改+建议"）；"需人工确认"项不得默认采纳；
5. 回写范围 = **枚举清单**：契约（§3/§4/§5）+ **接口.md 对应字段** + 落点表 + **`边界/`（仅当命中"第二个消费者"判据：差异约定对 ≥2 个应用/模块都必须一致遵守）**；**不含应用规范**——应用规范只由"应用接入/技术栈变更"这类显式事件更新（模块级对账不写它）；
6. 回写总契约索引。

### 3.2 停条件（命中立即停，不硬走完）

| 命中反例 | 动作 |
|----------|------|
| 差异成因是"需求本来就没实现"（代码缺功能），而非"代码偏离契约" | 停 → 重定向 `/module-plan`（语义变更写进计划的「语义增量」节），不得把缺失当差异回写 |
| **应用之间不一致**（如 web 端与移动端状态语义不同） | 停 → 只报差异，提示走 `/module-plan` 修代码；**不得把某一端写进契约** |
| 模块零实现（待实现模块） | 停 → 提示 `/module-plan {模块名}` 建首次建模计划 |
| 用户显式指定了另一种处理方式 | 以用户为准，记录覆盖原因 |

## 4. 产物补齐（契约 → 接口）

> 前提：契约与代码一致。**前置一致性检查必须逐项执行并报告结果**：

| # | 检查 | 通过标准 |
|---|------|----------|
| 1 | §5 应用落点文件存在 | 每个落点路径可 stat 到 |
| 2 | §4.2 接口路径可在代码中找到 | 逐个在对应服务代码中命中（路由/注解/方法名） |
| 3 | §3.2 枚举 code 与代码一致 | 状态/结果枚举 code 集合一致 |
| 4 | 接口.md 中标 ❌ 未接入的端 | **不算不一致**（是 backlog，不阻塞产物补齐） |
| 5 | 契约 §4 未越界（无字段名/类型/必填性/响应示例/错误码明细） | 概览四类内容之外无字段级明细 |

任一（1–3、5）不通过 → **停**，建议先走代码对账（第 5 项不通过则先把字段级内容迁进 `接口.md`）。

**步骤**：读契约（§3/§4/§5/§8.1/§8.2）与 `测试规范.md` → **接口.md**（字段级细节 + 服务归属/类型/消费方 + §5 接入状态）→ 回写契约 §8 引用。

> 测试文档和测试脚本属可选配套，不在此创建。如需生成，请使用 `/module-test {模块名}`。

## 5. 复合流程：代码对账 → 合并增量（无契约 + 有代码 + 带需求）

```
1. 代码对账建基线：分组差异清单（从零）→ 确认 → 生成契约 + 接口（建档方式记「代码对账」）
2. 基线确认：向用户展示基线契约要点，确认无误
3. 需求转计划：提示 /module-plan {模块名}，把需求写进计划的「语义增量」节（本技能不写未生效语义）
4. 计划实施完成后：回本技能走「合并增量」——把增量合并进契约 + 回写总契约（留痕在 git 提交信息 trailer）
```

**停止点**：代码对账基线未经确认，不进入第 3 步；第 3 步之后**不在契约里预写**任何未实施语义。

## 6. 生成文档的硬性要求

1. **导航区**：按契约模板头部导航区填（自动填值）；有探索记录时加「设计由来：{探索记录路径}」——只回链不复制（论证只留一处）；
2. **契约 §4 与接口.md 分工（防双维护）**：契约 §4 只保留"接口概览表 + 权限校验规则 + 接口对状态的影响"；**越界判据**——§4 出现**字段名/类型/长度/必填性/请求或响应示例/错误码明细/JSON 结构**即越界（`/module-review` 判 HIGH），一律改放 `接口.md`；**说明列 ≤120 字**；**端差异一律写契约 §5「差异说明」列**（≤2 句 + 回链；逐步操作手册/构建细节/历史沿革归应用规范或能力契约）；应用规范不承载模块级差异——它只写应用级技术栈与目录约定（一次性、稳定），跨应用共享内容上移 `边界/`；
   **契约四不写**：不写变更史（→ git）、不写代码清单（→ 回链代码路径）、不写跨应用机制（→ `边界/{能力}边界.md`）、不写其他模块的 SC 正文（→ 引用主载模块 ID）。§7 只写本模块不变量/陷阱；
3. **验收场景化（§8）**：按契约模板 §8.1/§8.2 写——Scenario 的 THEN 必须是**可观测结果**（库字段值 / 接口响应 / 页面表现），不写"功能正常"这类不可观测的话；
4. **绘图规范**：依赖图（§2）、状态机（§3）、页面结构（§5）一律 mermaid，禁止 ASCII；页面结构每端一张，端多折叠为链接；
5. **文件名与章节名固定中文**：解析器按 `NAMES.zh` 关键词定位，**改名必须同步**（写英文名如 `## 5. Application footprint` 不再被识别）——完整清单见 `docs/设计文档.md` §8.1；
6. **留痕在 git，不在契约 §9**：契约 §9 是固定指针节，**不再追加任何行**。追溯凭据写在代码提交信息（trailer：`模块:` / `计划:` / `契约:`——格式唯一权威见 AGENTS.md §5，本技能只引用不复述）；确认无语义变更时提交信息写 `契约:无需变更`。翻 `已合并` 的前提是增量已落账（契约 ⊆ 代码事实），与 §9 无关；
7. **建档（create 分支）专属**：契约 §2.1/§8.2 的信息来自计划的「建模补充」节（M1 依赖与集成点 / M2 验收 Scenario），**图取自计划 §1.3**（按图前粗体标注分拣：`**状态机**` → 契约 §3.2、`**页面结构 · 端名**` → 契约 §5 每端一张；无标注的图不进契约），§1 定位与 §2.2「不做什么」取自计划 §1，§3 schema / §4 路由权限 / §5 落点路径以**代码实际**为准（§6 标杆参考是建档时探测既有模块得来）——若缺建模补充节，**停并回报**"计划缺建模补充节"，不要凭空编造；建档后回写总契约（§4 索引表含依赖列 / §5 全景图 / §3 应用拓扑）；
8. **回写**：创建/更新后回写总契约 §4 模块索引表（列定义见该表表头），并据依赖列重绘 §5 全景图。

## 7. 完成

输出：处理方式与判定依据（含编号确认结果）+ 文件清单 + 产物范围（明确"未生成什么"）+ 合并状态变更（如翻 `已合并`）+ 下一步提示（`/module-review {模块名}`、`/module-plan {模块名} 归档`）。

## 8. 边界文档的生成与更新（回写期必经判定 + 探索吸收）

边界文档（`{文档根}/边界/{能力}边界.md`）没有独立写手——它有两个入口，本技能都是执行方：

- **入口一（回写期必经判定，主入口）**：合并增量（§2.1 第 5 步）与代码对账（§3.1 第 5 步）的回写范围枚举里，凡命中**"第二个消费者"判据**——该约定对 ≥2 个应用/模块都必须一致遵守——**必须**写/建边界文档，不再依赖任何人开口要求；
- **移动而非复制（硬规则）**：能力契约接管一条规则后，模块契约**删除正文**，只留一行回链（`> 委托给：边界/xxx §N`）；否则视为重复缺陷（`/module-review` #24 / #36）。新建/更新能力契约后回写 `总契约 §7 能力契约索引`；只剩 1 个消费者时解散回写，不留空壳；
- **入口二（探索吸收）**：用户要求把某主题结论落成跨模块/跨应用规则（如"把权限模型的结论写成边界文档"）；先用 `doc-framework list --explore` 定位 `已定案` 的探索记录（根目录 = 待吸收清单）；
- **判据**：结论属**多模块/多应用/跨应用共享能力** → 按 `templates/边界/{能力}边界.md.tpl` 新建或更新 `边界/{能力}边界.md`（工作流/附件/权限/服务间调用/事件与 MQ/鉴权网关/平台接入等）；**单模块特有规则并回该模块契约**（走 §1 处理方式），**单端特有机制并回应用规范（分册）**，不建边界文档；归属判据与"第二个消费者"规则的完整表述见 AGENTS.md §5 与 §3.1 第 5 步；
- **记账（与 /module-plan 同规则的机械记账权，仅记账不改内容；先写后移三步时序见 /module-explore §5）**：本技能特有第一步——边界文档**文首「最后更新」行**回链探索记录（边界文档没有变更记录节，历史归 git）；随后把该探索记录头部状态改 `已使用`、`结论去向` 补 `已并入→边界/{能力}边界.md`、**移入 `探索/归档/`**，正文**永不改写**；已被其他文档消费过的（状态`已使用`）不再移动，只追加第二条去向；
- **与 §1 三种处理方式的关系**：边界文档生成**不走**合并增量/代码对账/产物补齐——那三种针对模块契约与接口.md；本节是"探索 → 长期契约层"的直接通道，探索记录是被消费的输入而非真相来源（真相落进边界文档后，以边界文档为准）。
