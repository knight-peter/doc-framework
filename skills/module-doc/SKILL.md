# 模块文档技能（module-doc）

负责模块核心文档（契约 / 接口）的**创建与更新**。分工：**文档归 /module-doc、代码归 /module-code**，/module-review 兜底一致性；**探索与讨论归 /module-explore**；**语义变更归 /module-plan**（写进计划的「语义增量」节）。

> **触发**：`/module-doc {模块名}`。**零后缀、零参数**——模式由 AI 探测后带编号请你确认；强制模式回编号或用自然语言。

## 0. 上下文自动发现（零路径投喂 + 应用路由）

1. 读项目档案——**先读「应用清单」（路由表）**：应用 → 类型/代码根/规范文件/数据库/依赖；再读文档根、语言、通用约定、标杆映射、文档导航；
2. 读总契约——模块索引表、依赖矩阵、应用拓扑；
3. **应用路由**：确定本模块涉及的应用（已有模块读契约 §5 落点表；待实现模块读计划的「建模补充」M3 集成点，推断不出**只问一次**主责服务与涉及端）；
4. 涉及跨模块/跨服务能力时读对应边界文档（缺索引则扫 `{文档根}/边界/`）；
5. 发现档案缺登记时**提示回填档案**，而非反问用户要路径。

## 1. 三种模式（按"真相来源"分）

| 模式 | 真相来源 | 产出与停止点 |
|------|----------|--------------|
| **M 合并增量** | 已批准的计划「语义增量」 | **update 分支**（契约已存在）：把增量合并进契约 §3/§4/§5/§8 + 接口.md，**合并前以代码校正**；**create 分支**（待实现模块首次建档，契约不存在）：按增量 + 建模补充生成契约 10 章 + 接口.md，并**回写总契约**；两分支都：§9 记「合并（一句话增量摘要 + 回链凭据：`计划标识 @提交SHA`）」、把计划的 `合并状态` 翻成 `已合并` |
| **B 代码对账** | 代码 | **分组差异清单** → 分组确认 → 回写**契约 + 接口**（§9 标注来源=代码）；**待实现模块拒绝执行**（无代码可对） |
| **C 产物补齐** | 契约 | 前置检查通过后，产出**接口.md**；测试文档和脚本可通过 `/module-test` 按需生成 |

- **契约不承载未生效语义**：需求变更不再由本技能写进契约正文，而是 `/module-plan` 写进计划的「语义增量」节；实施后由 M 落账；
- **模式总数三个**：原先的"模式 A 需求驱动（契约先行）"已取消（待实现模块改走 `/module-plan` 的首次建模计划）。

### 1.1 判定：意图优先，状态校验（不可跳）

```
第 1 步：读用户意图（从话里取，不从状态猜）
   需求词（§1.4 词表）        → 语义变更，候选「/module-plan 增量」（见第 2 步）
   代码既成语（§1.4 词表）    → 候选 B
   补产物词（§1.4 词表）      → 候选 C
   合并/落账词（"计划完成了""落账""合并增量"）→ 候选 M
   无意图词                  → 进入第 2 步由状态推断

第 2 步：用仓库状态校验候选
   计划已完成 + 合并状态=待合并            → M（最高频入口）
   无契约 + 无代码（待实现模块）           → 【不归本技能】重定向 /module-plan（首次建模计划）
   无契约 + 有代码 + 需求词                → 【B→M 复合流程】（§5）：先 B 建基线，需求写进计划增量，实施后 M
   无契约 + 有代码（无需求词）             → B（从零生成 契约+接口）
   有契约 + 需求词                        → 【语义变更不归本技能】重定向 /module-plan（增量）；实施完成后再回来走 M
   有契约 + 代码词                        → B（分组差异回写）
   契约与代码一致 + 产物缺失               → C（前置检查见 §4）
   判定"不影响契约语义"                    → 【无需文档变更】结论（说明理由，不写 §9）

第 3 步：冲突/低置信 → 只问一个问题二选一；仍不成形 → 重定向 /module-explore
```

**三条反直觉规则**（必须执行）：

1. 用户显式意图 > 状态推断；**不得因为"代码恰好存在"就自动走 B**；
2. B 的触发条件是"用户确认代码是既成事实、不打算改代码"，不是"能读到代码"；
3. **无契约 + 有代码 + 需求词 = 复合流程**（先 B 建基线，再走计划增量，实施后 M），不是二选一。

### 1.2 确认门（任何模式首写前一律确认；编号 = 强制入口）

**固定格式**（事实 + 模式 + 产物 + 编号备选）：

```
探测事实：计划 2025-01-02-订单改造 状态=已完成、合并状态=待合并（增量 3 项）→ 候选 M（update 分支）
将写入：契约 §3/§4/§5/§8 + 接口.md；§9 追加「合并」行（增量摘要 + 回链凭据：`计划标识 @提交SHA`）
1) 确认按 M 执行    2) 改为 B（以代码为准对账）    3) 改为 C（只补产物）
```

- 回复**数字** = 精确切换模式并视为确认（封闭输入，不依赖语义解析）；
- 回复自然语言同样生效；**用户显式指定时 AI 必须遵从**（即使与探测冲突），并记一句"**用户强制指定，覆盖探测**"；
- 执行中命中 §3.2 停条件才再次打断；否则一次确认走完；
- **不得擅自翻 `合并状态`**：只有 M 完成合并后才翻 `已合并`。

### 1.3 探测规则表

| 探测事实 | 模式 |
|----------|------|
| 计划状态=已完成、`合并状态=待合并` | **M**（update；待实现模块则 create） |
| **无契约 + 无代码**（待实现模块） | **重定向 `/module-plan`**（首次建模计划；建档链路见 §2.4 的 create 分支） |
| **无契约 + 有代码 + 需求词** | **B → M 复合**（§5） |
| 无契约 + 有代码（无需求词） | B |
| 有契约 + 代码不一致（用户说"代码改了/同步"） | B |
| 有契约 + 用户描述的是需求变更 | **重定向 `/module-plan`**（语义变更写进计划的增量节） |
| 契约与代码一致，但 接口.md 缺失或不完整 | C |
| 有契约 + 用户明确说"补齐接口" | C |
| 任一模式判定"不影响契约语义"（纯实现/文案/样式） | **无需文档变更**（说明理由后结束）；真要把代码改掉 → 走 `/module-code {模块名}` **直改通道**（免计划，边界=契约 §5 落点） |
| 用户给的是**主题**而非模块名，且需求不成形 | 不猜 → 提示 `/module-explore {主题}` |

### 1.4 词表（冲突判定的可复现依据）

- **需求词**：新增 / 增加 / 改成 / 要支持 / 应该 / 需要（描述期望行为）
- **代码既成语**：代码已经改了 / 线上就是这样 / 现在已经是 / 同步一下（把代码当事实）
- **补产物词**：出接口 / 补接口 / 出方案
- **合并词**：落账 / 合并增量 / 计划完成了 / 建档（待实现模块）
- **冲突信号**：同时出现需求词与代码既成语；或状态与意图矛盾；或代码落点含 TODO/空实现标记 → 走"只问一个问题"档。

### 1.5 旧后缀兼容（不宣传，但识别）

`新建`→ 重定向 `/module-plan`（首次建模计划）｜`补文档`→B（无契约）｜`同步`→B（有契约，**以代码为准**）｜`改造`→ 重定向 `/module-plan`（语义变更走计划增量）。旧后缀只作为自然语言提示被识别，不再是正式语法。

## 2. 模式 M：合并增量（计划 → 契约，两分支）

> **前提**：计划状态=已完成（或有明确授权），且其「语义增量」已实施落地。合并**不是抄计划**——见 §2.3 铁律。

### 2.1 update 分支（契约已存在）

0. （推荐）先跑只读清单：`doc-framework check --draft-contract {计划路径}` —— 它按「目标位置」把每条增量映射到目标章节，**保证不漏条目**（不写文件）；
1. 读计划「语义增量」（ADDED / MODIFIED / REMOVED 三表 + `主计划` 列）与计划「关键设计决策」；
2. 按「目标位置」逐条定位契约章节（§3 数据模型 / §4 接口 / §5 落点 / §8 验收）与 `接口.md`；
3. **以代码校正**（§2.3）：字段名/类型、路由、权限标识、落点路径一律从代码取；
4. 写入契约 + 接口.md；接口.md §5 各应用接入状态按各端实际更新；
5. 契约 §9 追加**一行**：`来源=合并`、日期、**一句话增量摘要 + 回链凭据（`计划标识 @提交SHA`）**（有偏离则备注「实施偏离：计划 X → 实际 Y」）——**实施细节不抄进 §9**（类名/方法/行号/SQL 片段/取证过程属提交信息与计划；`check` 对单行 >300 字符给 ℹ️）；
6. 把计划的 `合并状态` 翻成 `已合并`；
7. 回写总契约（模块索引表 / 依赖矩阵；拓扑有变时同步 §3）。

### 2.2 create 分支（待实现模块首次建档）

> **建档九步**（首次建模计划实施完成后执行）：

```
① 探测 + 编号确认门（1 现在建档 / 2 稍后）；可先跑 `doc-framework check --draft-contract {计划路径}` 取建档清单
② 读入五类输入：计划的「语义增量」/「建模补充」/ 代码实际 / 契约·接口模板 / 总契约+应用清单+探索记录
③ 渲染契约骨架（模板 → 10 章）
④ 按 §2.4 映射表填 §2/§3/§4/§5/§8（目标语义来自增量 + 建模补充）
⑤ 以代码校正 §3/§4/§5（字段/路由/权限/落点）→ 不一致写入 §9 偏离备注
⑥ 填头部导航区（业务域 / 形态 / 主责服务 / 关联文档 / 标杆 / 核心文档回链）
⑦ §9 记一行 `来源=合并` + 一句话增量摘要 + 回链凭据
⑧ 生成 接口.md（§1–§4 取自代码，§5 接入状态按各端实际）
⑨ 回写总契约三处（§4 模块索引表 / §5 依赖矩阵与全景图 / §3 应用拓扑）→ 翻 `合并状态=已合并` → 自检 `check` + `/module-review` 检查 11
```

### 2.3 铁律（两分支共用）：以代码为准，不照抄计划

- **计划是设计意图，契约是已生效事实**：字段名/类型、路由路径/方法、权限标识、各端文件路径**一律从代码取**；
- 计划与实际不一致 → 契约写**代码值**，并在 §9 合并行备注「实施偏离：计划 X → 实际 Y」；
- 合并后立即自检 `check` + `/module-review` 检查 11（契约 ⊆ 代码事实）——**合并动作自带验收**；
- 增量落账后计划**归档**（需 `合并状态=已合并`，否则 `/module-plan` 拒绝归档）：归档会先校验契约 §9 已登记本计划、再把提交 SHA 写进该行、然后移入 `计划/归档/`（**不删除**——清理由人手动决定）——所以 M 落账时必须**把 §9 那行写全**（结论 + 理由一句话 + 回链凭据），别只写"已合并"；

### 2.4 映射表（增量 + 建模补充 + 代码 → 契约章节）

| 契约章节 | 来源 |
|----------|------|
| 头部导航区 | 计划头部（模块名 / 主责服务 / 涉及应用）+ 应用清单（类型层规范）+ 同型标杆 + 核心文档回链 |
| §1 模块定位 | 建模补充 §M1 / 计划「需求理解」+ 探索记录的"目标一句话" |
| §2 边界约定 | 建模补充 §M1（边界与「不做什么」）；§2.1 依赖以**代码实际调用**为准 |
| §3 数据模型 | 增量 ADDED 中 `契约 §3.x` 的行 + **代码实际 schema**；状态机图来自建模补充 §M2 |
| §4 接口概览 | 增量 ADDED 中 `契约 §4.x` 的行 + **代码实际路由与权限标识** |
| §5 应用落点 | 增量 ADDED 中 `契约 §5` 的行 + **各端实际文件路径**（每行必须真实存在，review 检查 11 会验） |
| §6 标杆参考 | 建档时探测：同业务域 / 同形态的既有模块 |
| §7 特殊约定与陷阱 | 实施中的实际坑（代码注释 / 计划「关键设计决策」） |
| §8 测试与验证 | 建模补充 §M4 Scenario + 计划验收标准（§8.1/§8.2/§8.3） |
| §9 变更记录 | **一行**：`来源=合并`、日期、**一句话增量摘要 + 回链凭据（`计划标识 @提交SHA`）** |
| §10 生产 SQL 登记 | 计划「回写清单」列出的 SQL（未执行则留空表） |
| 接口.md §1–§4 | **代码实际**（请求 / 响应 / 错误码 / 分页） |
| 接口.md §5 各应用接入状态 | 各端实际接入情况（实然） |
| 总契约 §4 / §5 / §3 | 模块索引表行 / 依赖矩阵行 + 全景图节点 / 应用拓扑（仅当引入新应用） |

## 3. 模式 B：代码对账（以代码为准回写文档）

> 护栏：**不允许直接覆盖**——先出分组差异清单、分组确认、登记来源。**待实现模块拒绝执行**（没有代码可对，硬停并提示先 `/module-plan`）。

### 3.1 步骤

1. 按应用清单**逐应用**到其代码根 glob 定位落点代码（`*Controller.java`、`views/*/{模块}/`、`pages/{模块}/`、`pages.json` 等；路径从清单派生，禁止写死目录名）；
2. 读各应用落点代码（Controller / Service / Mapper / 各端页面）；
3. 产出**分组差异清单**：

   | 组 | 内容 | 默认 |
   |----|------|------|
   | **必改** | 接口路径/方法、状态机与枚举 code、权限标识、应用落点 | 建议全接受 |
   | **建议** | 字段名称/类型、必填性、错误码文案 | 逐组确认 |
   | **仅登记** | 字段说明、枚举文案、注释级差异 | 默认只登记不改契约 |

   行格式：`| # | 对账项 | 组 | 契约现值 | 代码事实 | 建议动作 | 置信度 |`

4. **分组确认**（可"只接受必改+建议"）；"需人工确认"项不得默认采纳；
5. 回写范围 = 确认差异项影响的**全部下游文档**：契约（§3/§4/§5）+ **接口.md 对应字段** + 落点表；契约 §9 追加记录并**标注来源=代码**；
6. 回写总契约索引。

### 3.2 停条件（命中立即停，不硬走完）

| 命中反例 | 动作 |
|----------|------|
| 差异成因是"需求本来就没实现"（代码缺功能），而非"代码偏离契约" | 停 → 重定向 `/module-plan`（语义变更写进计划的「语义增量」节），不得把缺失当差异回写 |
| **应用之间不一致**（如 web 端与移动端状态语义不同） | 停 → 只报差异，提示走 `/module-plan` 修代码；**不得把某一端写进契约** |
| 模块零实现（待实现模块） | 停 → 提示 `/module-plan {模块名}` 建首次建模计划 |
| 用户显式指定了另一模式 | 以用户为准，记录覆盖原因 |

## 4. 模式 C：产物补齐（契约 → 接口）

> 前提：契约与代码一致。**前置一致性检查必须逐项执行并报告结果**：

| # | 检查 | 通过标准 |
|---|------|----------|
| 1 | §5 应用落点文件存在 | 每个落点路径可 stat 到 |
| 2 | §4.2 接口路径可在代码中找到 | 逐个在对应服务代码中命中（路由/注解/方法名） |
| 3 | §3.2 枚举 code 与代码一致 | 状态/结果枚举 code 集合一致 |
| 4 | 接口.md 中标 ❌ 未接入的端 | **不算不一致**（是 backlog，不阻塞 C） |
| 5 | 契约 §4 未越界（无字段名/类型/必填性/响应示例/错误码明细） | 概览四类内容之外无字段级明细 |

任一（1–3、5）不通过 → **停**，建议先走 B（第 5 项不通过则先把字段级内容迁进 `接口.md`）。

**步骤**：读契约（§3/§4/§5/§8.1/§8.2）与 `测试规范.md` → **接口.md**（字段级细节 + 服务归属/类型/消费方 + §5 接入状态）→ 回写契约 §8 引用。

> 测试文档和测试脚本属可选配套，不在此创建。如需生成，请使用 `/module-test {模块名}`。

## 5. 复合流程 B → M（无契约 + 有代码 + 带需求）

```
1. B 建基线：分组差异清单（从零）→ 确认 → 生成契约 + 接口（§9 记"来源=代码"）
2. 基线确认：向用户展示基线契约要点，确认无误
3. 需求转计划：提示 /module-plan {模块名}，把需求写进计划的「语义增量」节（本技能不写未生效语义）
4. 计划实施完成后：回本技能走 M → 合并增量 + §9 记"来源=合并" + 回写总契约
```

**停止点**：B 基线未经确认，不进入第 3 步；第 3 步之后**不在契约里预写**任何未实施语义。

## 6. 生成文档的硬性要求

1. **导航区**：头部包含导航区（自动填值）：
   ```markdown
   > 关联文档：总契约.md、边界/{能力}边界.md、规范/应用-{涉及应用标识}.md
   > 关联代码：{标杆模块} → {代码路径}
   > 回链：本模块 接口.md（测试为可选配套，由 /module-test 生成）
   ```
2. **契约 §4 与接口.md 分工（防双维护）**：契约 §4 只保留"接口概览表 + 权限校验规则 + 接口对状态的影响"；**越界判据**——§4 出现**字段名/类型/长度/必填性/请求或响应示例/错误码明细/JSON 结构**即越界（`/module-review` 判 HIGH），一律改放 `接口.md`；端差异写在应用规范或契约 §5"差异说明"列；
3. **探索记录回链（如存在）**：契约导航区加"设计由来：探索记录路径"——只回链不复制（论证只留一处）；
4. **验收场景化（§8）**：§8.1 验收标准清单（标注对应场景编号）+ **§8.2 关键验收场景用 Scenario 写法**（`#### Scenario: SC-n` + WHEN/THEN，THEN 写可观测结果）。
5. **绘图规范**：依赖图（§2）、状态机（§3）、页面结构（§5）一律 mermaid，禁止 ASCII；页面结构每端一张，端多折叠为链接；
6. **文件名与章节名固定中文**（**唯一一套，v2.6.0 起不再支持英文产物命名**——英文只影响文档内容）：`{文档根}/模块/{模块名}/{契约.md,接口.md,测试.md,test.sh}`，档案 `项目档案.md` 的 `## 应用清单`，契约 `## 5. 应用落点`。解析器按 `NAMES.zh` 的关键词定位，**改名必须同步**（清单见框架仓库 `docs/设计文档.md` §8.2）；写英文名（如 `## 5. Application footprint`）不再被识别；
7. **§9 来源标注**（四值）：`需求`（旧项目历史记录）/ `代码`（模式 B 对账）/ `实现`（/module-code 直改通道的免计划小改，"未动语义"）/ `合并`（M 把已批准增量落账）。**来源=合并的行必须回链凭据（`计划标识 @提交SHA`）**——凭据必须"不会消失"（归档计划可由人手动清理，不得指向会消失的文件），为空则不得翻 `已合并`；
8. **建档（create 分支）专属**：契约 §1/§2/§3/§8 的信息来自计划的「建模补充」节（M1–M4；§6 标杆参考是建档时探测既有模块得来）——若缺失，**停并回报**"计划缺建模补充节"，不要凭空编造；建档后回写总契约三处（索引表 / 依赖矩阵与全景图 / 应用拓扑）；
9. **回写**：创建/更新后回写总契约模块索引表（模块名、主责服务、各应用落点、标杆参考、边界依赖）。

## 7. 完成

输出：模式与判定依据（含编号确认结果）+ 文件清单 + 产物范围（明确"未生成什么"）+ 合并状态变更（如翻 `已合并`）+ 下一步提示（`/module-review {模块名}`、`/module-plan {模块名} 归档`）。
