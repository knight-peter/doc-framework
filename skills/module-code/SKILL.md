# 模块代码技能（module-code）

负责**执行改动**——**以计划的「语义增量」+ 契约不变量为约束、白名单为边界**，不创建/修改四件套文档（文档归 /module-doc）、不创建/修订计划（计划归 /module-plan）。

> **触发**：显式触发词为 `/module-code`（仅英文技能名触发）。
> **设计原则**：**授权粒度 ∝ 爆炸半径**——改一个文案的授权，不该和"改状态机 + 加表 + 三端联动"共用一套文档；但**降级必须由人确认，AI 不得自我授权**。

## 0. 通道判定（先定通道，再执行）

| 触发 | 定位方式 |
|------|----------|
| `/module-code {计划路径}` | **计划通道**：路径直达（绝对或相对路径，相对以项目根为基准）；模块名从路径 `模块/{模块名}/计划/` 或计划文档「依据模块契约」行解析 |
| `/module-code {模块名}` | glob `模块/{模块名}/计划/*.md`：**有**「已批准」计划 → 列出供选择（编号）；**无** → **探测直改通道**（§0.2） |

**红线**：计划通道只执行「已批准」状态的计划；「待审核 / 修订中 / 已废弃」一律拒绝执行，提示先用 `/module-plan` 处理。

### 0.1 三通道与判据（意图优先、状态校验）

自上而下判定，**先命中先定**——判据客观可查证，不靠"感觉改动大不大"：

| # | 判据（命中即取该通道） | 通道 |
|---|------------------------|------|
| 1 | 触及契约语义：契约 §3/§4 出现**新**字段/表/接口/状态机状态/权限标识，或改动 §8 验收场景、跨应用一致性不变量 | **完整计划**（语义变更写进计划的「语义增量」节） |
| 2 | 含 SQL 变更 / 生产数据变更（契约 §10 需登记） | **完整计划** |
| 3 | 涉及 **≥2 个应用**（哪怕纯文案） | **轻量计划**（逐应用表态需要留档） |
| 4 | 单应用 + 不触语义 + 无 SQL + 预计 ≤5 文件 + 无设计决策 | **直改通道**（免计划，§0.2） |
| 5 | 其余（单应用但改动面大、或需要留决策） | **轻量计划** |

> 判据 1 的客观形式：**"这个改动能不能在契约里找到对应条目？"**——找得到是实现，找不到就是语义变更。
> **禁止 AI 自降级**：任何"免计划"判定都必须先给编号确认门（§0.2），用户确认后才动手；用户显式指定通道时必须遵从并记录。

### 0.2 直改通道（免计划小改：一次确认、一个边界、一行留痕）

**边界来源是契约 §5 应用落点表**（应用级），不是计划——契约本就是长期真相，"这个业务在哪些应用存在"天然定义了"这次能碰哪些应用的代码根"。

```
探测：契约 §5 落点 = svc-order + app-mobile；本次未触及契约 §3/§4 任何条目
判定：实现级改动 → 直改通道（免计划）
边界：仅这 2 个应用的代码根（应用级）；预计 3 个文件；无 SQL
1) 直改（按此边界）   2) 改走轻量计划   3) 改走完整计划（语义写进「语义增量」节）
```

- 用户回编号（或自然语言"就直改"）后才动手；契约缺失或 §5 落点为空 → **不走直改**：**待实现模块**（代码库零实现）→ 走 `/module-plan {模块名}` 计划通道（首次建模计划）；**有实现无契约** → 提示 `/module-doc {模块名}`（模式 B）先补契约与落点；
- 每次 edit/write 前自检：目标文件归属的应用必须 ∈ 契约 §5 落点，**越界即停**；
- **自动升级**：执行中发现要动契约语义或用 SQL → **立即停**，**升级为完整计划**，把语义写进计划的「语义增量」节 → 计划通道；已改部分如实汇报，不"顺手"改完；
- **硬禁用**（不进判据权衡，直接拒绝免计划）：SQL 与生产数据、状态机、权限标识、跨应用一致性不变量、公共契约/共享库；
- 收尾：`doc-framework diff-check --module {模块名}` 自检（与 CI 同款），留痕见 §5.1。

## 1. 加载上下文

1. **计划通道**：加载实施计划文件，校验状态=已批准；读取**计划形态**（完整/轻量）、逐应用表态、变更文件清单、实施顺序、关键设计决策、接口兼容性声明、验收标准、回写清单；**直改通道**：无计划，边界取契约 §5 落点；
2. 解析模块名（传路径时），读模块四件套——计划「语义增量」= 本次目标语义（实施约束），契约 = **长期不变量**（§2 边界 / §3 状态机 / §5 应用落点 / §7 陷阱）、接口.md 字段细节（已生效的服务端真相）；待实现模块此刻无契约，约束只有增量 + 应用/类型层规范；
3. 读项目档案「应用清单」——**只加载表态「改动」的应用**的规范（`规范/应用-{应用标识}.md`）与标杆代码（可见性 ≠ 上下文）；直改通道只加载契约 §5 落点应用的规范与标杆；映射缺失时 glob 找同类实现并提示回填档案；
4. 涉及跨模块/跨服务能力时读对应边界文档。

## 2. 路径白名单（执行边界，每次写文件前自检）

白名单按通道不同，**粒度不同但都必须越界即停**：

| 通道 | 白名单 | 粒度 |
|------|--------|------|
| 计划通道（完整 / 轻量） | 表态「改动」应用的代码根 ∩ 计划变更文件清单 | **文件级** |
| 直改通道 | 契约 §5 应用落点表中登记的应用的代码根 | **应用级**（有意取舍：防"改到别的应用"；文件级细节交 `/module-review` 事后审计 + 测试 + git 回滚） |

- 每次 edit/write 前：目标路径必须在白名单内——**越界即停**，不偷偷改；
- 确需改动白名单外的文件（如契约缺口：接口没覆盖、落点未登记）→ 走纠偏回路：停下 → 定性（代码 Bug vs 契约缺口）→ `/module-plan 修订`（已批准 → 退回修订中 → 补表态/补清单；**语义缺口写进计划的「语义增量」节** → 重新批准）；**有实现无契约**时改用 `/module-doc {模块名}`（模式 B）先补契约 → 批准后白名单更新再继续；
- 边界情况：某应用代码根为 `./` 时前缀约束失效，退化为**纯文件级清单**（只允许动清单逐条列出的文件，宁严勿宽）。

## 3. 按依赖序实施

按计划「实施顺序」节执行（缺省时按默认依赖序）：

1. SQL（进对应服务的 `{代码根}/sql/change/` 目录）；
2. **主责服务**——接口**目标语义以计划的「语义增量」节为准**（接口.md 是已生效的服务端真相，随实施由 `/module-doc` M 合并回写），数据模型、API、状态机、特殊约定必须遵守增量 + 契约长期不变量；
3. 下游/聚合服务——对着计划的「语义增量」中的接口语义实现转发/聚合（接口.md 是已生效真相，由 `/module-doc` M 在实施后回写），禁止倒推；
4. 逐端实施——每端完成后**独立自检**再进入下一端；
5. **增量 + 契约不变量作约束**：实施中**偏离计划**（如实际字段名/路径与增量不一致）→ **以代码为准继续，不回头改计划正文**；在回写阶段记录偏离（契约 §9 记「实施偏离」，由 `/module-doc` M 合并时写入）；不得绕过契约的长期不变量直接改代码。

> 直改通道通常只涉及 1 个应用，跳过步骤 1–3（含 SQL 的一律不走直改）。

### 3.1 任务清单逐项勾选（进度事实源）

计划的「四、任务清单」是执行序列与进度事实源：**每完成一项就地把 `- [ ]` 改为 `- [x]`**（立即勾选，不攒到最后补）。

- **只勾选事实完成的项**——禁止提前勾选、禁止"基本完成"式勾选；
- 某项无法完成或需变更范围 → 不勾选，走纠偏回路（回 `/module-plan 修订` 调整任务清单），不得私自跳过；
- 汇报与收尾时给出进度（`已完成 x/总 y`），未完成项列明原因；
- **存在未勾选项时，不得把计划状态登记为「已完成」**。

### 3.2 作用域授权（已批准计划能改什么、不能改什么）

批准的对象是**作用域**，不是任务清单——这条是"小改单能承接多次小改"的基础：

- **作用域 = 逐应用表态 + 变更文件清单**（即白名单）。**扩作用域必须回 `/module-plan` 修订**（已批准 → 退回修订中 → 补表态/补清单 → 重新批准）——红线不变；
- **作用域不变的前提下，允许向「任务清单」追加任务项**（记账，不算修订）：典型场景是一份轻量计划在有效期内承接同一范围的多次小改，避免每次小改都新建计划 + 重新批准；
- **状态为「已完成」的计划不得追加任务**——那是新改动，应新建计划或先退回修订中；
- 追加任务前后都要跑 `doc-framework diff-check {计划路径}` 自证仍在范围内。

## 4. 一致性自检

对照检查：代码 ↔ 实施计划 ↔ 契约 §4 / 接口.md（直改通道无计划，对照契约 §5 落点与 §3/§4 约束）。

- **完成度核对**：任务清单逐项对照实际代码/产出——已勾选但无对应实现（假勾选）、有实现但未勾选（漏勾）都要纠正；两者不一致即如实修正勾选状态；
- 发现偏差（路径/字段/权限标识）→ 列出"待同步项"：计划内偏离 → 以代码为准，留待 `/module-doc` M 合并时写入契约 §9「实施偏离」；体系外已改/无契约 → 提示 `/module-doc {模块名}`（模式 B 对账）；
- 实施中出现**超出计划增量**的契约语义/权限层面变化（状态机新增状态、权限标识变更）→ **立即停**，回 `/module-plan` 修订，把语义补进「语义增量」节，重新批准后再继续；
- 状态机/权限标识在各应用间必须一致（跨应用不变量）——发现某端自定义语义，按契约纠正；
- **直改通道额外自检**：`doc-framework diff-check --module {模块名}`（越界即报错），并确认改动确实没触及契约语义——若触及，按 §0.2 自动升级。

## 5. 回写（交付义务，不可跳过）

按实施计划"回写清单"逐项登记：

- **任务清单全部勾选**（存在未勾选项时不得登记「已完成」；确实未完成的，保持「实施中」并说明）；
- 契约变更记录追加一行（**事实登记**：改了哪些字段/接口/状态机），并**标注来源=代码**（/module-doc 模式 B 亦同；`合并` 行由 M 合并增量时写入，本技能不写；来源四值 `需求 / 代码 / 实现 / 合并`）——供 /module-review 的 §9 来源查账；
- 含需生产执行的 SQL 时，契约 §10 生产环境 SQL 执行登记追加一行（**所属服务** + 文件引用 + 影响摘要，状态=待执行；不复制 SQL 正文）；
- **接口.md §5 各应用接入状态更新**（本次实施的应用打勾）；
- 契约 §5 应用落点表同步（新增落点/差异说明变化时提示 /module-doc）；
- 测试执行记录；
- 实施计划状态登记为「已完成」（**事实登记**，状态归 /module-plan 的约定，本技能只登记实施类状态）；
- 提示 `/module-doc {模块名}`（M 合并增量落账：同步接口.md 并更新总契约索引——**索引由 /module-doc 维护**）；
- **首次建模计划专用**（判定式：计划**无** `依据模块契约` ∧ **有** `依据探索记录`）：实施完成后给一次编号确认门——`1) 现在由 /module-doc {模块名} 建档（M 的 create 分支）  2) 稍后`；**不得擅自翻计划的 `合并状态`**（翻标记是 M 合并的职责）；
- 提示 `/module-plan {模块名} 归档`（归档是 /module-plan 的职责，本技能不移动计划文件）。

### 5.1 直改通道的回写（轻量，但不可省）

直改没有计划文档，回写只剩两处——**一行留痕 + 一次对账**，这是免计划换来的最小代价：

1. 契约 §9 变更记录追加一行：日期 + 来源=**`实现`** + 一句话（如"订单列表文案调整（不影响契约语义）"）——`实现` 表示"只动了实现、没动语义"（来源四值 `需求 / 代码 / 实现 / 合并` 之一）；
2. 提交信息首行带 `模块:{模块名}`（供 `diff-check --module` 与 /module-review 事后对账）；
3. 不改契约 §5 落点表、不改接口.md（语义没动）——一旦发现需要动，立即按 §0.2 升级通道，不得就地"补一下"。

**边界**：/module-code 只做事实登记；**语义变更归 `/module-plan`（计划的「语义增量」节）**，契约与接口.md 的合并落账归 `/module-doc`（M），计划创建/修订/归档归 `/module-plan`，提示后等确认，不得自行改动。

## 与 /module-doc、/module-plan 的协作约定

| 场景 | 流程 |
|------|------|
| 正向开发（大改） | `/module-plan {模块名}`（完整计划：语义写进「语义增量」节）→ 批准 → `/module-code`（实施+回写）→ `/module-doc {模块名}`（M 合并增量落账） |
| 改造（存量模块） | `/module-plan {模块名}`（新计划/修订：语义写进「语义增量」节）→ 批准 → `/module-code`（实施+回写）→ `/module-doc {模块名}`（M 落账） |
| **待实现模块**（代码库零实现） | `/module-explore`（探索记录强制落盘）→ `/module-plan {模块名}`（首次建模计划）→ 批准 → `/module-code`（实施；无契约不变量可依，只有增量 + 规范）→ 编号确认门 → `/module-doc {模块名}`（M 的 create 分支建档 + 回写总契约） |
| **小改（单应用、不触语义）** | `/module-code {模块名}` → 探测 + 编号确认（**直改通道**）→ 实施 → `diff-check --module` + 契约 §9 一行留痕 |
| **小改（跨应用、不触语义）** | `/module-plan {模块名}`（**轻量计划**：表态+清单+任务）→ 批准 → `/module-code {计划路径}` → 逐次在作用域内追加任务 |
| 计划未批准 | `/module-code` 拒绝执行 → 提示 `/module-plan` 处理 |
| 白名单外需求 | 停下 → `/module-plan 修订`（语义补进「语义增量」节）→ 重新批准后继续；有实现无契约时 `/module-doc {模块名}`（模式 B）先补契约 |
| 直改途中发现语义变更 | **立即停** → `/module-plan`（升级完整计划，语义写进「语义增量」节）→ 计划通道重做 |

/module-review 兜底校验文档与代码一致性（多应用对账 + git diff 对账 + 回写查账 + 直改通道事后审计）。
