# 模块测试技能（module-test）

负责模块测试文档（`测试.md`）和黑盒测试脚本（`test.sh`）的**生成、讨论定稿与执行**。测试是**可选的**——简单模块可以不建测试，只靠 `/module-review` 做一致性审计。

> **触发**：`/module-test {模块名}`（生成/讨论定稿），`/module-test {模块名} 执行`（校验并执行）。
> **设计原则**：测试文档 = 契约的映射。从契约+接口可推导测试，不依赖人肉维护。

## 0. 前置条件

```
/module-test 所有形态的前提：
  ✅ 模块契约.md 存在（§4 接口概览 + §8.2 验收标准 SC-n）
  ✅ 模块接口.md 存在
  ❌ 任一缺失 → 提示"请先通过 /module-doc 创建契约和接口文档"
```

## 1. 两个入口场景

### 场景 1：生成/讨论定稿

```
/module-test {模块名}
```

**用途**：从契约生成测试初始草稿，与用户多轮讨论后定稿。

**步骤**：

1. 读 模块契约.md
   - §4 接口清单 → 决定黑盒用例骨架
   - §8.2 SC-n  → 决定验收场景对应关系
   - §5 应用落点 → 决定端层/编排层 checklist 是否需要
   - §3 数据模型 / §3.2 状态机 → 决定白盒断言是否需要（有持久化状态时）
   - §2 边界 → 辅助理解模块范围

2. 读 模块接口.md
   - 接口路径/方法/参数 → 黑盒 curl 步骤的具体参数

3. 读 `测试规范.md`（`{文档根}/测试规范.md`）
   - §1.1 适用规则 → 判定本模块应覆盖的测试层
   - 四层判据：
     - 黑盒（接口层）：**所有模块必备**
     - 白盒（库层）：有持久化状态/流程反写/软删除/乐观锁时必备
     - 端层：契约 §5 有前端端落点时
     - 编排层：契约 §5 涉及 ≥2 个服务端应用时

4. 生成初始草稿：
   - **测试.md**（规格文档）：
     - §1 测试目标（从模块定位 + SC-n 推导）
     - §2 适用层与依据（按测试规范 §1.1 判定结果）
     - §3 前置条件（服务地址、流程定义、表结构、权限）
     - §4 测试账号矩阵（从权限规则推导）
     - §5 验收标准（引用契约 §8.2 SC-n，不重新定义）
     - §6 端到端测试用例（每个 SC-n 对应一个或多个用例）
     - §7 库层断言（白盒，按 §3/§3.2 判据决定是否启用；指向项目自有测试或写 SQL 文本）
     - §8 编排层用例（跨服务时）
     - §9 端层冒烟 Checklist（有前端端时）
     - §10 验证 SQL（白盒时）
   - **test.sh**（黑盒脚本）：
     - 从测试.md 的用例生成 curl 步骤
     - 参数化 BASE_URL（每个服务端应用一个）
     - PASS/FAIL 断言计数
     - 不含删除/清理逻辑（测试数据保留供人工复核）

5. 展示给人 → 多轮讨论修改（增删用例、调整账号、修改断言细节）→ 定稿

**不生成**：
- 不生成 `test.white.sh`。白盒内容写入 测试.md §7 库层断言节，指向项目自有测试代码或 SQL 文本。

### 场景 2：校验并执行

```
/module-test {模块名} 执行   （中文别名）
/module-test {模块名} --run  （英文别名）
```

**用途**：校验测试文档与契约一致，执行黑盒测试脚本，生成版本化测试报告。

**步骤**：

1. **一致性校验**（未通过则不走执行）：
   - 测试.md 中引用的所有 SC-n 在契约 §8.2 中存在
   - 契约 §8.2 的所有 SC-n 在测试.md 中都有对应用例
   - 不一致 → 报差异清单，提示先走场景 1 同步

2. **执行 test.sh**：
   - 环境变量从当前会话/配置取（BASE_URL、账号密码等）
   - 捕获每步的 PASS/FAIL

3. **读取契约版本号**：
   - 解析 契约.md §9 变更记录表格 → 统计数据行数 N
   - 版本号 = `v{N}`

4. **写入测试报告**：
   - 目录：`{文档根}/模块/{模块名}/测试报告/`
   - 文件：`v{N}.md`
   - 格式见 §1.1

5. **输出结果**：
   - PASS/FAIL 汇总
   - 每条失败详情（期望 / 实际 / 根因推测 / 建议通道）
   - 不自动跳转

## 1.1 测试报告格式

```markdown
# {模块名} 测试报告 v{N}

> 执行时间：{YYYY-MM-DD HH:mm}
> 契约版本：v{N}（§9 共 {N} 行）
> 执行方式：test.sh

## 结果概要

PASS={n}  FAIL={n}

## 失败详情

### F-1 {失败用例名}
- **期望**：{期望值}
- **实际**：{实际值}
- **根因推测**：{分析}
- **建议通道**：{/module-code 或 /module-plan}
- **理由**：{简短理由}

## 环境

- BASE_URL_SVC_MAIN: http://{实际值}
- 测试账号：{账号名}
```

## 1.2 测试报告版本命名规则

```
契约.md §9 行数 → 版本号 → 文件名

  §9 有 1 行（初始化建档） → v1 → 测试报告/v1.md
  §9 有 2 行（一次合并增量） → v2 → 测试报告/v2.md
  §9 有 3 行（两次合并增量） → v3 → 测试报告/v3.md

每次执行测试时，module-test 读取当前契约 §9 行数 N，
写入 测试报告/v{N}.md。如果已存在同名文件则覆盖。
```

## 2. 失败路由

module-test 执行后发现失败时，输出每条失败的建议通道，**不自动跳转**：

```
建议通道判据（复用 /module-code §0.1 三通道逻辑）：
  /module-code：单接口问题，不触契约语义，直改可修复
  /module-plan：涉及语义变更、多应用、需要分析方案
```

由人决定后续操作：

```
你：/module-code ...
 或：/module-plan ...
```

## 3. 产物结构

```
模块/{模块名}/
├── 契约.md              ← 不动。§8.1 保留路径引用，§8.2 保留 SC-n
├── 接口.md              ← 不动
├── 测试.md              ← 规格文档。模块唯一，从契约+接口生成，可讨论修改
├── test.sh              ← 黑盒脚本。从 测试.md 用例生成，参数化
└── 测试报告/             ← 目录。按契约 §9 行数命名，每次执行生成一份
    ├── v1.md
    ├── v2.md
    └── ...
```

白盒测试不生成独立脚本，写入 测试.md §7 库层断言节：

```markdown
### 7. 库层断言

| # | 断言 | 验证方式 |
|---|------|----------|
| 1 | 主表 status 反写为"待审核" | `services/order/src/test/java/OrderServiceTest.java` |
| 2 | process_instance_id 非空 | `SELECT process_instance_id FROM t_order WHERE order_no = 'xxx'` |
```

- 项目有自有测试代码 → 指向对应测试类/方法
- 项目没有自有测试 → 写 SQL 文本，人工执行

## 4. 不做什么

- **不创建/更新契约**（归 /module-doc）
- **不创建/更新接口文档**（归 /module-doc）
- **不修改代码**（归 /module-code）
- **不创建/修订计划**（归 /module-plan）
- **不自动跳转修复通道**（输出建议，等人决定）
