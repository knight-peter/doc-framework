# doc-framework：面向文档开发体系

把一套在真实全栈项目中验证过的「契约文档 + 测试文档 + 实施计划」开发方法——**面向文档开发**（Document-Oriented Development）——抽象为**可跨项目复用的方法论资产**：文档模板 + 六个 skill + 安装工具。

> AI 深度参与开发的全栈项目越多，这套体系越值钱——它给 AI 定"规矩"：**文档永远反映真实代码，代码永远长在既有架构上**。
> 支持**多应用工作区**：一个项目可登记 N 个前端应用 + N 个后端服务（不同技术栈），档案「应用清单」统一路由，契约保持业务语义唯一真相，应用只是落点。

**设计取向**：skill 不焊死任何技术栈（项目特定约定全在「项目档案」，换技术栈只换档案）· **契约 = 当前代码的语义映射**，是业务的唯一语义真相 · 上下文从体系中来（档案 → 总契约 → 标杆 → 边界），用户只给业务需求。

## 术语表（契约模型）

> 一句话模型：**契约 = 当前代码的语义映射（应然 ≡ 实然，永不领先代码）；语义变更 = 计划的「语义增量」，批准后被授权、实施后由合并增量落账。**

| 术语 | 定义 |
|------|------|
| **待实现模块** | **代码库中尚无任何实现的模块**（无目录 / 无路由 / 无表 / 无接口 / 无契约）。**只要有任何一处实现，它就不是待实现模块**。英文同义词 `greenfield`。 |
| **首次建模计划** | 待实现模块的计划：必须 `完整` 形态、含全量「语义增量」（几乎全是 ADDED）与「建模补充」节。 |
| **存量模块（已建档）** | 有实现 + 有契约：改动走"计划增量 → 合并增量的 `update` 落账"。 |
| **存量模块（未建档）** | 有实现 + 无契约（接入体系时已有代码）：走 `/module-doc` **代码对账**补建（不走计划）。 |
| **语义增量** | 计划里的 `Delta` 节：ADDED / MODIFIED / REMOVED 三张固定列表 + `主计划` 列，是**待生效语义**与 `/module-code` 的实施约束；**批准 = 语义定稿**。 |
| **合并状态**（三值） | `待合并` / `已合并`（可带日期，如 `已合并（2026-01-02）`）/ `无需合并`；三值外的旧写法不再识别（命名只中文，见[文档体系](#文档体系初始化后生成)）；`无需合并` 用于空增量（纯实现改动）或已废弃计划。 |
| **合并增量** | `/module-doc` 的合并处理：`update` = 存量模块按增量落账，`create` = 待实现模块首次建档 + 回写总契约。 |

> **最容易混的一处**：**存量模块未建档 ≠ 待实现模块**——只要有一行代码 / 一张表 / 一个接口，它就是存量模块，走代码对账补建；待实现模块是"计划时刻"的状态，实施一落代码就转成存量模块。三态的判定与路径全表见[设计文档 §3.1](docs/设计文档.md)。

## 六个技能的使用方式

六个 skill 用 `/命令` 显式触发（防误触发，不用自然语言关键词），**DSH 只识别英文技能名**。核心分工一句话：**探索归 /module-explore、文档归 /module-doc、计划归 /module-plan、代码归 /module-code、测试归 /module-test、检查归 /module-review**——各司其职，谁都不越界。记忆点：**探路、写文档、写计划、写代码、写测试、收尾检查**。各技能的职责边界全表见[设计文档 §4.1](docs/设计文档.md)，细节详见各 `SKILL.md`。

### 技能速览

**0. `/module-explore` —— 探索与讨论（可选前置）**：需求模糊、方案取舍、不熟代码库、范围存疑时先做一次**零承诺**对话（调研代码、比较方案、把问题问清楚）。产出默认不落盘（决策留在对话里），**待实现模块场景强制落盘**；硬护栏：不写代码 / 契约 / 计划，只谈要不要做、放哪、走哪条路、范围，**不设计字段接口**。

**1. `/module-doc` —— 模块文档（契约 / 接口）**：核心文档聚合在 `模块/{模块名}/` 下——`契约.md`（语义约束，10 章）、`接口.md`（字段级**服务端真相**，唯一事实源）。按**真相来源**自动分三种处理方式（**合并增量** / **代码对账** / **产物补齐**），由 AI 探测、确认门带编号可强制切换。核心纪律：**契约永不领先代码**——语义变更写进计划的「语义增量」节，实施后由合并增量落账。路由要点与三种方式的真值来源见[设计文档 §4.2](docs/设计文档.md)。

**2/3. `/module-plan` 与 `/module-code` —— 计划与代码**：`/module-plan` 建计划（待审核）→ `/module-code` 执行（**调用即批准**：计划还是「待审核」时自动登记「已批准」后实施；逐项勾选任务）→ 登记「已完成」→ 归档。**并非所有改动都值得一套完整计划**——`/module-code` 按判据自动分三通道，见[小改动通道](#小改动通道直改与轻量计划)；状态机与归档规则见[计划 30 秒](#计划30-秒说明)。

**4. `/module-review` —— 模块审查**：读档案（注入技术栈特有检查项）→ 总契约 → 核心文档（契约 / 接口）→ 对照代码逐项检查；输出分级问题清单 `CRITICAL / HIGH / MEDIUM / LOW` + **回写查账**（跑 `check` 看「文档落后检查」有无未回写提示、§10 生产 SQL 登记、接口.md 与代码一致性、总契约索引）；**CRITICAL 与 HIGH 清零才提示可提交**。

**5. `/module-test` —— 模块测试（可选）**：测试 = 契约的映射，从契约 + 接口推导测试规格，不依赖人肉维护。两种场景：**生成 / 讨论定稿**（`/module-test {模块名}`）→ 读契约与接口 → 生成 测试.md + test.sh → 多轮讨论调整 → 定稿；**校验并执行**（`/module-test {模块名} 执行`）→ 校验 SC-n 一致性 → 执行 test.sh → 输出版本化测试报告到 `测试报告/`。白盒断言写入 测试.md §7 库层断言节，不生成独立脚本。不影响核心工作流，简单模块可跳过。

**触发说明**：`/技能名` 手势仅支持小写字母 / 数字 / 连字符；也可用自然语言描述（如"用模块代码技能…"），AI 会按技能目录自行加载。

## 计划：30 秒说明

**计划是当时的最新方案快照**（人读层 §1 讲清"需求 / 实施后结果 / 思路"）**，契约才是长期真相**。一次需求一份计划，从「待审核」走到「已完成 / 已废弃」即可**归档**；归档时校验 `合并状态=已合并` 且契约已承接 → 移入 `计划/归档/`（**归档不删文件**——清理由人手动决定；**长期追溯靠 git 提交信息的 trailer（`计划:{计划标识}`）**，不依赖计划文件存活）。**计划不记修订史与决策史**：正文始终只有最新方案（就地改写），被否理由归探索记录、历史归 git。

状态：`待审核 → 已批准 → 实施中 → 已完成`，另有 `修订中`（改计划必经）与 `已废弃`。**「已批准」有两个入口**：用户确认，或 `/module-code` 的**调用即批准**（显式调用执行「待审核」计划时，它先登记「已批准」再实施——「修订中 / 已废弃 / 已完成」不在此列）。状态机图与两类计划的落盘位置见[设计文档 §3.6](docs/设计文档.md)。

**语义增量是语义变更的唯一载体**（ADDED / MODIFIED / REMOVED 三表 + `合并状态`，**批准计划 = 语义定稿**）；合并状态的三个取值与定义见[术语表](#术语表契约模型)，其组合后果（`已完成 + 待合并` → `check` 硬报错且拒绝归档等）见[设计文档 §3.4](docs/设计文档.md) 不变量 I2/I4。

**三条纪律**：① 任务只勾事实完成的项，**未勾完不得登记「已完成」**；② 实施完成 ≠ 可以归档——归档是 `/module-plan {模块名} 归档` 的独立动作，时机由人定（可能还要等生产 SQL 执行、等验收）；③ 跨模块计划放全局 `计划/`，只能用 `{计划路径}` 直达。

**常见误解**：计划确认后不会自动实施（必须显式 `/module-code`——而显式执行「待审核」计划就是批准，不必先手动改状态）· 已批准计划不能直接改 · 任务不能最后一起勾 · 「已完成」的计划不能追加任务 · 小改不一定建计划（见下节）。

> 完整规则（11 条常见误解等）见[设计文档 §3.7](docs/设计文档.md)。

## 小改动通道：直改与轻量计划

> 设计原则：**授权粒度 ∝ 爆炸半径**。三条底线不可让渡——**AI 不能自我授权**（必须有一次人的确认）、**不能改到范围外的应用**、**事后可追溯**。

`/module-code` 按三通道判据自动分派（先命中先定：触契约语义 / 含 SQL → **完整计划**；跨应用 → **轻量计划**；单应用 + ≤5 文件 + 无决策 → **直改通道**免计划）——判据表与判据 1 的客观形式（"能不能在契约里找到对应条目"）唯一权威源是 `skills/module-code/SKILL.md` §0.1，本文不复述。直改通道的编号确认门、边界来源（契约 §5 应用落点）、硬禁用清单与留痕见[设计文档 §3.5](docs/设计文档.md)；改完跑 `doc-framework diff-check --module {模块名}` 对账。途中发现要动契约语义 → 立即停，升级完整计划（已改部分如实汇报）。

**轻量计划**：保留 `§1 需求与思路（压缩版：四小节各一句，图按需）/ 逐应用表态 / 变更文件清单 / 任务清单` 四节，头部标 `> 计划形态：轻量`，**不含「语义增量」节**（发现触语义 → 升级完整计划）。**批准的对象是作用域**（表态 + 清单）：扩作用域 = 扩权，必须退回「修订中」重新批准；**作用域内追加任务项属记账**，可直接更新——一份轻量计划能承接同范围的多轮小改，配合 `list --stale {N}` 与 `/module-plan {模块名} 归档`，归档从"每改一次"降为"每迭代一次"。

> 成本对比（5 步 → 1 命令 + 1 次确认）与防滥用设计见[设计文档 §3.5](docs/设计文档.md)、§3.8。

## 安装

### 方式 A：npm git 依赖（推荐，适合有 package.json 的全栈项目）

```json
{
  "dependencies": {
    "doc-framework": "git+https://github.com/knight-peter/doc-framework.git#<最新 tag>"
  },
  "pnpm": {
    "onlyBuiltDependencies": ["doc-framework"]
  }
}
```

> **`<最新 tag>` 怎么取**：`git fetch --tags && git describe --tags --abbrev=0`；没有检出时 `git ls-remote --tags git@github.com:knight-peter/doc-framework.git | sed 's|.*refs/tags/||' | grep -v '\^{}' | sort -V | tail -1`。
> **本文件不写死版本号**——写死的示例会随发版腐坏（且示例里的版本一旦没有对应 tag，git 依赖会静默回落到默认分支最新提交）。版本口径见[设计文档 §9.3](docs/设计文档.md)。

`pnpm install` 后自动完成：`skills/*` → 项目级 skill 目录（默认 `.agents/skills/`，可经 `doc-framework.config.json` 配置）、`doc-framework/` 骨架目录（`模块/`、`边界/`、`规范/`、`计划/`、`探索/` + 引导 README）、`接入指南.md` → 项目根、`AGENTS.md` 写入接入引导（**已初始化项目自动跳过引导**）。

### 方式 B：一键安装脚本（无 package.json 的项目）

```bash
curl -fsSL https://raw.githubusercontent.com/knight-peter/doc-framework/main/install.sh | bash
```

> 脚本内部默认经 SSH 克隆仓库；若本机 SSH 22 端口不可达（如代理 / VPN 拦截），先指定可用的仓库地址再执行：
>
> ```bash
> export DOC_FRAMEWORK_REPO="https://github.com/knight-peter/doc-framework.git"
> curl -fsSL https://raw.githubusercontent.com/knight-peter/doc-framework/main/install.sh | bash
> ```
>
> （环境变量需 `export` 后单独一行；`VAR=x curl | bash` 的写法传不到管道里的 bash。）

**与方式 A 行为一致**（安装 skills → 预置 `doc-framework/` 骨架目录 → 生成《接入指南.md》→ 写入 `AGENTS.md`）。

## 接入初始化（一次性）

安装后项目根出现《接入指南.md》。对 AI 说 **"初始化项目"**（或 AI 按 `AGENTS.md` 引导主动提示）：

- **既有代码库**：AI 扫描代码 → 生成档案草案（逐项标注证据来源与置信度）→ 开发者确认 → 提炼第一份契约（标杆）→ 生成文档骨架；
- **全新项目**：AI 提问（技术栈 / 约定 / 业务域）→ 生成档案 + 骨架。

> **渲染纪律**：所有骨架文档一律从官方模板渲染生成（模板位置见《接入指南.md》「模板来源」），**禁止凭空自创结构**；`{占位符}` 必须全部替换为项目实际值，完成后运行 `npx doc-framework check` 自检。

初始化完成后 AI 自动清理一次性引导：移除 `AGENTS.md` 接入引导段、删除《接入指南.md》与 `doc-framework/README.md`（骨架引导）。

```mermaid
    AA -->|"无"| AC["完成：提交信息带 trailer + 计划标「已完成」"]
    AC --> AR["/module-plan 归档（校验 合并状态=已合并 → 移入 计划/归档/）"]
```

> **异常分支**：计划处于「修订中 / 已废弃」时 `/module-code` 拒绝执行，退回 `/module-plan` 处理（「待审核」不再是拒绝理由——显式调用即批准）；**直改途中发现语义变更** → 立即停，升级完整计划、计划通道重做（已改部分如实汇报）。

## 文档体系（初始化后生成）

```
doc-framework/
├── 项目档案.md          ← 唯一需人工确认的文件（应用清单 = skill 路由表；通用约定全局段+应用覆盖）
├── 总契约.md            ← 总索引：业务域、应用拓扑、模块索引表（主责服务+各应用落点）、依赖矩阵+全景图、跨模块业务流程、维护规则
├── 测试规范.md          ← 通用测试方法论（接口层/库层/端层/编排层 四层验证、缺陷闭环）
├── 接口规范.md          ← 全局接口约定（REST/认证/统一响应外层与错误码/分页/接口层字段语义；兼容性红线在总契约维护规则）
├── 规范/                ← 三层 + 分册：类型-前端、类型-后端（类型层共性）+ 应用-{应用标识}（每应用一份差异 = 索引）+ {应用标识}-{主题}（深度技术主题分册，按需）
├── 边界/                ← 跨模块/跨服务/跨应用共享能力（工作流/附件/权限/服务间调用/事件与MQ/鉴权网关/平台接入等）
├── 计划/                ← 跨模块实施计划；归档/ 为已归档计划（不自动删除）
├── 探索/                ← 探索记录（/module-explore 落盘的单次决策记录；根目录 = 探索中 + 已定案待吸收，归档/ = 已使用 + 已作废）
└── 模块/{模块名}/       ← 模块聚合资产（业务语义唯一真相，应用只是落点）
    ├── 契约.md          ← 语义约束（10 章：主责服务声明 + §5 应用落点表 + §8.2 验收场景 + §10 生产 SQL 登记；§9 为固定指针节——**历史归 git，本文件只记当前真相**，mermaid 图）
    ├── 接口.md          ← 字段级服务端真相（唯一事实源）：服务归属/类型/消费方 + 各应用接入状态
    ├── 测试.md
    ├── test.sh          ← 多服务 BASE_URL 参数化
    └── 计划/            ← 单模块实施计划（YYYY-MM-DD-{主题}.md：形态=完整/轻量）；归档/ 为已归档计划
```

**上面这棵树即完整的路径清单**——不另设"产物命名表"（同一批路径写两处必然漂移，与体系自己的"规则归属单一职责"纪律冲突）。

**产物命名只有一套：中文**：文档根固定 `doc-framework/`，目录 / 文件 / 章节 / 头部字段 / 枚举值一律中文；**英文只影响文档内容，不影响命名**。命名清单的运行时权威是 `plan.js` 的 `NAMES.zh`（文档侧视图见[设计文档 §8.1](docs/设计文档.md)，决策与理由见 §8.3）。

## 升级

**怎么升**：

- 方式 A：更新依赖版本后 `pnpm install`（lockfile 锁死时 `pnpm update doc-framework`；store 复用跳过 postinstall 则 `pnpm rebuild doc-framework`），或直接 `npx doc-framework sync`
- 方式 B：重新执行安装脚本

**三条边界**：

- **只动 skill 文件**：`sync` / 安装脚本**绝不**重命名、移动或改写你的 `doc-framework/` 文档根与 `AGENTS.md`（除首次安装写入引导段）——文档资产的任何变化一律由人手工执行，命令最多给提示；
- **本地定制过的 skill 自动跳过**（版本标记 + 逐文件 sha256 比对），不会被覆盖；
- **templates 升级只影响新项目初始化**：已初始化项目的档案与契约是自有资产，永不回灌。

> 升级后**重开一个会话**，新 skill 才会进上下文。
> **升级是单向的**：体系不兼容旧文档结构，已初始化项目要**按逐版本迁移清单人工对齐到最新**（清单见[设计文档 §9.3](docs/设计文档.md)；交给 AI 逐批执行的**可粘贴提示词**见 [`docs/老项目升级上下文.md`](docs/老项目升级上下文.md)：先只读勘察 → 差异报告 → 升框架 → 逐批迁移 → 验收报告）。

## 常见问题（FAQ）

**Q1：`pnpm install` 装完了，但 `.agents/skills` 里没有 skill？**

pnpm v10 默认不执行依赖包的生命周期脚本，必须先配置 `pnpm.onlyBuiltDependencies: ["doc-framework"]`（见方式 A 配置）。若配置后仍缺失，多半是 **store 复用跳过了 postinstall**（安装输出显示 "reused N"），执行 `pnpm rebuild doc-framework` 强制重跑安装脚本。

**Q2：git 依赖要不要带版本号？**

建议钉**最新 tag**（取法见[安装](#方式-anpm-git-依赖推荐适合有-packagejson-的全栈项目)，本文件不写死版本号）：`git+...#<最新 tag>`。不带 `#ref` 时解析的是默认分支（main）的**最新提交**，而非最新标签；且 lockfile 会把解析到的提交 SHA 锁死，之后 main 有新提交也不会自动更新，需要 `pnpm update doc-framework`（或删除 lockfile 重新 install）。

**Q3：`doc-framework sync` 提示"跳过（本地已定制）"？**

这是防漂移设计：版本标记 `.doc-framework.json` 按相对路径（如 `module-code/SKILL.md`）逐文件记录 sha256，**判定粒度是整个 skill 目录**——该目录里任一文件与官方版本不一致，整个目录就被视为本地定制、跳过不覆盖。

放弃定制恢复官方版本：跑 `pnpm rebuild doc-framework`（安装脚本**无条件先删后拷**）。注意 `sync` 在版本标记已是当前版本时对该目录整体跳过，所以**"删掉某个文件再跑 sync"找不回来**。

**Q4：安装失败残留了部分 skill 目录？**

安装中途失败会留下不完整目录且没有版本标记。重装或 `pnpm rebuild doc-framework` 会先删后拷自动覆盖，无需手动清理。

**Q5：升级会覆盖项目里的文档吗？**

不会——升级只换 skill 文件，`templates` 的改动只影响新项目初始化（见[升级](#升级)）。

**Q6：`doc-framework check` 是干什么的？**

校验文档体系完整性（**退出码 0=通过 / 1=有硬问题**；ℹ️ 提示项不影响退出码；`--strict` 把提示类判据升为 ⚠️）：骨架完整性、应用清单健康、计划体检（含语义增量与合并状态 I2/I3）、**文档落后检查**（契约是否还对得上当前代码，依 git 历史判定）、**规范层归属判据**（变更痕迹 / 跨应用同题 / 小节越界 / 索引↔分册）、文档结构版本哨兵、占位符残留与引导清理。

> **完整判据清单不在本文件复述**（会随实现漂移）：见 `doc-framework --help` 与[设计文档 §6.3](docs/设计文档.md)。

**Q7：`doc-framework diff-check` 是干什么的？**

**提交前 / CI 对账**（退出码 0=通过 / 1=有越界）：给**计划路径** → 按计划的「逐应用表态 + 变更文件清单」对账；给 **`--module <模块名>`** → 直改通道对账，按契约 §5 落点表推导应用级白名单。把 `/module-review` 的多应用对账前置到提交前，零 prompt 依赖。

> 参数全集（`--base` / `--staged` / `--strict`）与**管辖范围**（只评判应用清单登记的应用内的越界；管辖不到的文件只给一行 ⚠️、默认不影响退出码）见 `doc-framework --help` 与[设计文档 §6.4](docs/设计文档.md)。

**Q8：`doc-framework list` / `show` 是干什么的？**

**只读查询**（除 `sync` 外所有命令都只读，可进 CI）：`list` 列在途计划（状态 / 形态 / 合并状态 / 涉及应用 / 任务进度），`list --explore` 聚合探索记录（`探索/` = 探索中 + 已定案待消费，`探索/归档/` = 已使用 + 已作废），`show <计划路径>` 给单个计划的结构化视图（含推导出的白名单与任务进度）；`list --stale <N>` 是**批量归档入口**（默认视图不含"已完成"，批量归档要 `--stale <N> --all`）。

> 选项全集见 `doc-framework --help`；输出契约（`--orphans` 的「在途」口径、`Next:` 引导等）见[设计文档 §6.5](docs/设计文档.md)。

## 使用纪律

1. **语义先于代码、记录后于代码**：语义变更（字段 / 接口 / 状态机 / 权限标识 / 应用落点）先在计划的「语义增量」节定稿，代码照增量实现；实施后由 `/module-doc` 合并进契约与 接口.md——**契约永不领先代码**。"代码在前"的例外（既有代码无契约 / 待实现模块）见[术语表](#术语表契约模型)与[日常开发流程](#日常开发流程)；
2. **测试→契约回写闭环**：发现问题先定性"代码 Bug vs 契约缺口"，涉及约定变化必回写契约；
3. **契约只记当前真相，历史归 git**：查历史用 `git log -- <模块代码路径>`（提交信息带 `模块:` / `计划:` / `契约:` trailer）；**不把变更记录写进任何文档**；
4. **计划是事实登记**：任务只勾事实完成的项，未勾完不得登记「已完成」；归档前校验 `合并状态=已合并`（见[计划 30 秒](#计划30-秒说明)）；
5. **通道可以降级，边界与留痕不能**：小改免计划必须过编号确认（AI 不得自我授权），改完跑 `diff-check --module` 并在提交信息写 `契约:无需变更`——省的是仪式，不是纪律。
